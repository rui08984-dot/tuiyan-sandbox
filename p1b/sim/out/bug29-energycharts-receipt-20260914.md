# bug-29 收据：Energy-Charts 解析器两处口径错误 —— UTC 日过滤（均值偏差 ~8%）＋ 分辨率无关硬阈值（永久卡死）（2026-09-14）

## 一句话

解析器把 API 按**该国本地日**返回的窗口又用 **UTC 日**二次过滤 → 每天丢掉本地 00:00–02:00 的 8 个点（15 分粒度）⇒ 均值偏差 **~8%**；
完成度判据写死 `n<80`（按 15 分粒度标定）⇒ **小时粒度**国家（比利时，满日仅 24 点）**永远 pending、卡死 2.5 个月**。
修为「本地日全窗口 ＋ 按实测步长自适应完成度」。**已核存量 24 行 0 翻转**（偏差真实但未改任何结论 ⇒ 不回改历史数据）；
修后结清积压：**已解 1238 → 1263**（14 条过期未结清单全部收口）。

## 一 · 病象与根因

| 项 | 内容 |
|---|---|
| 病象 ① | **均值偏差 ~8%**：API 以 `start=end=<本地日>` 调用时返回**被查国家的本地日**窗口（实测 es 2026-06-25：`ts = 2026-06-24T22:00Z ~ 2026-06-25T21:45Z`，即本地 06-25 全天）；解析器却按 `toISOString().slice(0,10)`（**UTC 日**）过滤 ⇒ 本地 00:00–02:00 的 8 点被判到前一天丢弃 |
| 偏差实测 | fr/Solar **−8.33%**（7974.0773 → 7309.5708）｜es/Solar **−7.96%**（11452.3182 → 10540.6250）；账本行 id=1761 修复前后实录与直测**同值**（交叉印证，见 §二） |
| 病象 ② | **永久卡死**：be（比利时）为**小时粒度**（满日 24 点），`n<80` 硬阈值 ⇒ 恒判「未满当日」⇒ id=1785/1789/1791/1793（matures 2026-06-25）卡死 2.5 个月 |
| 根因 | `p1b/scripts/corpus-resolve.cjs` `energycharts_daily_mean`：① UTC 日过滤 ② 完成度用写死的点数阈值 |

> 病象 ② 的实质：把「**数据没到**」与「**口径不匹配**」混为一谈——阈值表达的是"整日数据齐不齐"，但整日的点数本身取决于时分辨率。

## 三 · 修复

代码：`p1b/scripts/corpus-resolve.cjs` `energycharts_daily_mean`（两处口径）：

1. **直接采用 API 返回窗口**（即本地日）——不再按 UTC 日二次过滤；
2. **完成度自适应**：取实测步长 `step`（秒）→ 期望整日点数 `round(86400/step)` → `ratio = n/expect`，`< 0.9` 才判「未满当日」；
3. note 增带**口径披露**：`（N 点，满日 M 点·K 分粒度，本地日全窗口口径）`——时分辨率与口径从此可核。

**修后自证**（daemon `--confirm` 实录）：

```

resolved id=1785 … 均值=5.3333MW（24 点，满日 24 点·60 分粒度，本地日全窗口口径）
```

⇒ 15 分粒度国家 n=96（不再丢 8 点）；小时粒度国家 n=24 直接正确结算（不再卡死）。

## 六 · 教训（可复用）

1. **第三方 API 的"日"是本地的还是 UTC 的，必须实测**——本 API 用 `start=end=<日>` 时按被查国家本地日返回；再按 UTC 日过滤 ＝ 悄悄削掉首尾。凡"日期窗口 + 时区"组合，**只认 API 返回窗口，不自造过滤**。
2. **完成度判据不得写死点数阈值**，应基于**实测步长自适应**——否则数据源一改时分辨率就永久 pending（把"数据没到"伪装成"未满当日"）。
3. **「卡住不结」本身就是信号**：本轮修 bug-28 顺路排查积压，才挖出 bug-29。积压应 routine 探测（不只盯错判，也盯不判）。
4. 修口径类 bug 的标准动作：**先量化偏差 → 再全量重算存量核查翻转 → 0 翻转才免回改**；有翻转则须回改＋留痕（不可逆账本就高代价，故顺序不能反）。
