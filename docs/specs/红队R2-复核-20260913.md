## §2 修法评审（F2 / F3 / F4）

口径事实按用户指示不再重证（design §4 分母＝提交总题数属实）。以下只评审**修法本身**的硬伤。

### §2.1 队列制 / cohort 口径（F2＋F3 的修法）

R1 建议：可判定率改为**提交时判定**（分子＝判据冻结∧锚可机检，不要求已 resolve）；三指标一律**按到期月分桶**，未到期单列 pending。

**硬伤 1 ｜ 与 design §4.1③ 的「checklist_hash 联动」规则冲突，且会污染 3 个冻结 PREREG 的选题口径。**
- design:137 原文：「③**指标定义改动＝预注册修订（checklist_hash 联动）**，禁逐月改线。」
- 但 `checklist_hash` 同时是冻结实验的**题源选择键**：`PREREG-RB-v1-待确认.md:9`（360 条…checklist_hash=v2）、`PREREG-RC-v1-待确认.md:9`（题源不变…checklist_hash=v2）、`p1b/scripts/judge-runner.cjs:43`（`pr.checklist_hash = 'v2'`）、`rb-score.cjs:49`、`rc-score.cjs:104`。
- 后果：若照 §4.1③ 把 G2 指标版本「联动」进 `checklist_hash`（升 v3），上述选择语句的**总体静默改变**，R-B/R-C 的复现锚（PREREG 四要素之「复现设计」）随之失效——而 PREREG 是最高权威（`docs/specs/README-总索引.md:5`）。
- **建议**：**不要复用 `checklist_hash`**。新增独立列 `g2_regime`（或 `metric_version`），题源键 `checklist_hash` 冻结不动；§4.1③ 的「联动」改写为指向新列。这是修法落地的**前置条件**。

**硬伤 2 ｜ 「按到期月分桶」当前没有可靠的到期日字段。**
- `g2-report.cjs:93` 的 M4 草案用 `evidence[].resolve.date | meta.eventDate | meta.month`；脚本:108 自注「**meta.month 无年份（如 09/10/11），故单列标注**」。实跑输出同时出现 `2026-09` 与 `2026-09（日粒度·取月）` 两个桶（同月被拆两行）。
- 后果：cohort 分母会重复/漏计；且 `resolve.date` 只覆盖部分题（实测 901 条未解题里有 resolve.date 的只落到 2026-02..2026-10）。
- **建议**：迁移新增 `matures_at`（DATE，写端落题时算好并校验非空），或一次性回填把 `meta.month` 补上年份；**不要**直接拿草案的字符串桶当判据。

**硬伤 3 ｜ cohort 会立刻暴露 262 条「已到期未结算」，naive 实现可能让读数更低。**
- 实测 `resolve.date < date('now') AND outcome IS NULL` → **262 条**（wide_backfill 225、b3_backfill 37；最早 2026-02-25，最晚 2026-09-12）。
- 后果：若分子仍沿用「resolved+voided」，这 262 条全进分母不进分子 ⇒ 队列口径读数**可能低于现状 40.1%**，与修法初衷相反；根因不是口径而是**结算积压**（daemon 未覆盖 wide/b3 两 kind）。
- **建议**：cohort 落地前先结清这 262 条（或单列 `overdue` 并给处置 SLA）；分子必须改成 R1 的原意「提交时冻结∧锚可机检」，否则与 F2 病灶同构。

**硬伤 4 ｜ backfill 的「到期」语义与 realtime 不同，不能同桶。**
- design §4.1 让 backfill 计入可判定率/争议率、只排除吞吐；但 backfill 的 `resolve.date` 全在历史（2024-01…2024-11），落桶后会与 realtime 的 2026 队列同轴比。
- **建议**：cohort 保留 R3 的 realtime/backfill 分窗**再乘**到期月（二维），且 backfill 的「到期月」定义为落库前置窗而非历史事件月，否则 backfill 独占早期桶、把 realtime 队列读数比得虚高。

**迁移代价**：g2-report.cjs（1 文件）＋ 一次库迁移（`g2_regime`/`matures_at` 两列）＋ 262 条积压结算；PREREG 三件**不改**（这正是硬伤 1 的收益）。

### §2.2 物理分库分表（F4 的修法）

R1 建议：`predictions`（题面+判据+cutoff）与 `truth_vault`（真值+resolve 参数）分离；truth_vault 只允许 resolver 读；回测引擎以只读题面视图运行，以「能否 SELECT 到真值」为复测判据。

**硬伤 1 ｜ 「真值」与「resolve 参数」现在同住 `evidence_json[0]`，而后者是 resolver 的输入。**
- `corpus-resolve-daemon.cjs:339` 取 `p.evidence_json`，`:344` 读 `ev[0].resolve`，`:50` 用 `resolve.date` 判到期，`:307-330` 用 `resolve` 过参数安全门。
- 后果：把 `resolve` 一起搬进 vault ⇒ **断掉 daemon 取数**；只搬 `truth_preview` ⇒ 留不下「题面/判据与真值分离」的完整语义（`resolve.date/threshold` 本身就是判据）。
- **建议**：明确三分——`predictions`（题面+cutoff+锚 id）／`resolution_spec`（resolve 参数，daemon 可读）／`truth_vault`（outcome+truth_preview，仅 resolver+scorer 可读）。

**硬伤 2 ｜ 爆炸半径 ＝ 24 个脚本 ＋ 4 个 src 文件读 `outcome`，且当前**没有角色隔离**。**
- 实测 `grep outcome`：p1b/scripts 命中 24 个 .cjs（rb-score.cjs:49、rc-score.cjs:104、rb-attribution.cjs、report-layered.cjs、report-murphy.cjs、ts-rebacktest.cjs、ablation.cjs、g2-report.cjs:30/37、corpus-resolve-daemon.cjs…）；p1b/src 命中 4 个（predictionsStore.cjs 的 calibration/l0Gate/listUnresolved、routes/audit.js:66-72、routes/predictions.js、routes/verdicts.js:161/165、adapters/avalon.js）。
- 后果：分库后每处都要改跨库（ATTACH）或改读视图；漏一处就得到**静默空结果**（SQLite 不报错，只返回 0 行）。今天「哪些进程是 participant／referee」没有任何声明或代码约束。
- **建议**：先落一张「进程角色表」（participant／scorer／resolver），再用 `ATTACH` 视图过渡（保住 24 处读取路径），**不要**一次性改所有脚本。

**硬伤 3 ｜ 与「账本不可变 ＋ PREREG 快照」的关系未定义；且分库不增加回滚能力。**
- `PREREG-RB-v1-待确认.md:17` 要求「库快照 hash 随报告落盘」；分库把一份快照变两份，hash 语义要重定义。
- p1a.db 现被 `p1a-terminal/.gitignore:4 (*.db)` 排除（`git check-ignore` 实测），新增 truth_vault.db 同样不进 git ⇒ **分库毫不增加**回滚能力，F12 的「无版本化路径」依旧。
- **建议**：F4 验收判据写成可执行断言（在回测进程里 `SELECT … FROM truth_vault` 期望 no-such-table/denied）；PREREG 快照改为「题面库＋vault 库」双 hash；若与 F12 同修，统一走「每日快照＋hash」。

**优先序结论**：F2/F3 修法**可现在做**，但必须先落「独立 `g2_regime` 列 ＋ `matures_at` 字段 ＋ 262 条积压结算」三件前置；F4 修法**不应现在做**，应在 D2 回测引擎立项时作为其验收前置（角色表 → 视图过渡 → 物理分库）。

### §2.3 修法之外的本轮实测新发现

**N1 ｜ `baseline_brier` 从未写入：design §3 的「跨层比较禁令技术实现」是空挂点。**
- design:100 要求「报表必须成对出示 layer_brier 与 baseline_brier 的差值」；实测 `SELECT COUNT(*) FROM predictions WHERE baseline_brier IS NOT NULL` → **0**，批量脚本无一写该列 ⇒ 禁令只有文字、没有读数。

**N2 ｜ `public_exposure` 在 879 行上为 NULL，偏离 design §3 的「他层 0」。**
- 实测非空 **624** 行；NULL 的 879 行覆盖 7 个 kind（wide_backfill 280／wide_forward 183／forward_batch_b2 136／forward_batch 112／oct_forward 69／b3_backfill 52／b3_forward 47），全部来自那 4 个脚本——它们**根本没传** `publicExposure`（漏传，不是拼错）。
- 后果：design:101「L4 必填，他层 0」在 58% 行上不成立；任何 `WHERE public_exposure = 0` 的统计会静默漏掉这 879 行。F16 守卫只能拦「拼错的键」，**原理上拦不住「漏传」**。

**N3 ｜ 根 `.gitignore:10` 注释与事实相反。**
- 注释写「p1a.db 本体入库，wal/shm 不入」，但 `git check-ignore -v p1a-terminal/data/p1a.db` → `p1a-terminal/.gitignore:4:*.db` ⇒ 本体也被排除。文档失实（F12 旁证）。

**N4 ｜ G2 争议率（M2）结构性恒 0，是「未实现」而非「达标」。**
- `g2-report.cjs:61-67`：库内无 void/rejudge 表，`voidedRows`/`rejudgedRows` 硬编码 0，`rate2 = 0/602 = 0%` 判「达标」。三指标里唯一「达标」的一项其实是空实现。
