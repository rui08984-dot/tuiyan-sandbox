## §3.5 融合架构：forward 与 backfill 是同一条管线的两种模式【2026-09-12 队长追加】

> 用户指出的关键洞察：**两者共用同一条管线骨架，且可完全并行执行**（非串行）。
> 【修正记录】本文件 v1 曾误写「不是并列，是上下游」——经用户指出后于 2026-09-12 修正为「并行 + 共用 + 局部基率复用」。

```
              同一套 corpus 管线（共用：基率计算 / Q0 门 / resolver 框架 / 落库路径）
              ├─ forward 模式：对未来出题 → 真预测 → 全额计入 G2 吞吐（主力）
              └─ backfill 模式：对历史出题 → 补样本厚度 → 只计质量指标（辅助，见 R3）
```

**【2026-09-12 队长修正（用户指出记忆偏差）】两种模式「可完全并行」——不是串行管道。**

上一版我写成「不是并列，是上下游」属于**过度纠正**：把「基率复用」这一处**局部**关系，错说成了全局串行顺序。正确表述是：

| 关系 | 正确说法 |
|---|---|
| **执行层面** | **完全并行** —— 两条线可同时跑、可同时大批量铺量（各自独立出题、独立 resolve），互不阻塞 |
| **基础设施层面** | 共用同一套管线骨架（基率计算 / Q0 门 / resolver / 落库），故新源接入一次、两条线都能用 |
| **局部数据关系** | 仅**基率计算**处 forward 可复用 backfill 算出的历史基率（这是一处复用，不是串行依赖；forward 也能自算 archive 基率） |

**实务含义（用户原话「直接可以并行，而且可以一下子多搞几个」）**：
- 两线**同时开跑**，不需要等谁先完成；
- 新数据源接入后，**同一个源可同时出 backfill 与 forward 两类题**（如天气：历史年份出 backfill、未来 16 天出 forward）；
- 铺量可**成倍扩**：源越多、每个源出的题越多，两线各自线性增长。
