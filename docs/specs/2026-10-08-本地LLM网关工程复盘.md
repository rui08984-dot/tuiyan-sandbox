## 1. 系统形态（抽象）

一段话讲清拓扑，后面所有教训都挂在这个结构上：

```
 客户端（多个 Agent）
      │  OpenAI 兼容 HTTP
      ▼
 本地网关（Go，单二进制，带系统托盘）
      │  出口选择：轮询 / 固定 / 直连
      ▼
 本地代理侧车（<sidecar>，提供 127.0.0.1:21001+ 的 socks 入口）
      │  每个 socks 入口 = 一个不同的出口 IP
      ▼
 上游 LLM 服务（按出口 IP 计额度）
```

三个关键点，也正是三类 bug 的高发区：

1. **出口是"每次连接"决定的**，所以任何连接复用都会破坏轮换；
2. **"可用性"是推断出来的**，不是事实，所以任何单次采样都可能说谎；
3. **侧车是独立进程**，所以它的生命周期必须显式设计。

## 2. 七条教训

### 教训 1 · 连接池会悄悄架空你的出口轮换

**现象**：网关配置成"按请求轮换出口"，但监控显示所有请求都从同一个 IP 出去，轮换**完全没生效**。

**根因**：Go 的 `http.Transport` 默认开启 keep-alive。轮换是靠 `DialContext` 回调实现的，而 **`DialContext` 只在"新建连接"时被调用**。连接一旦建立就被复用，于是：

```
请求 1 → 新建连接 → DialContext → 出口 A
请求 2 → 复用连接 ────────────────→ 出口 A   ← 期望 B
请求 3 → 复用连接 ────────────────→ 出口 A   ← 期望 C
```

**修法**（一行）：

```go
t.DisableKeepAlives = true
```

代价是每请求一次 TCP（含 TLS）握手。对本场景（请求间隔以秒计）完全可接受。

**验证**：修前把侧车日志开到 debug，6 次请求只用了极少数出站连接；修后同样 6 次请求用了 **7 个不同出口**（`out-02/03/04/05/61/62/63`）。

> **可迁移性**：任何"用 `DialContext` / 自定义 Dialer 做分流、轮换、限速"的代理都有这个坑。
> 判断方法很简单：**打日志看"出口选择"和"实际出站连接"是不是一一对应**。

### 教训 2 · 把"一次采样"当"全局状态"，是最常见的可用性 bug

这条是本次**影响最大**的一条，因为它同时制造了"该可用的不可用"和"面板与事实不符"两类问题。

**现象**：面板上 6 个模型标着"已限额"，但逐个用真实请求去测，**全部 3/3 成功**（11 个模型合计 22/22）。

**四个叠加缺陷**：

| # | 缺陷 | 后果 |
|---|---|---|
| a | 健康检查只走**一个出口**，结论却当**全局** | 一次坏运气 = 模型被判死刑 |
| b | 状态**没有有效期**（`ProbeResult` 里有时间戳字段，但从未被使用） | 一次判决影响整个检查周期（180 分钟） |
| c | 按结论**破坏性删除**模型（从 `/v1/models` 拿掉） | 客户端**根本选不到**本来可用的模型 |
| d | **真实请求成功不校正状态** | 面板与事实长期背离 |

**修法（四处都要）**：

**a. 结论加有效期（TTL）**

```go
const stateTTL = 30 * time.Minute

func FreshState(r ProbeResult) string {
    if r.State == "" {
        return StateUnknown
    }
    if r.At > 0 && time.Since(time.UnixMilli(r.At)) > stateTTL {
        return StateUnknown   // 过期按"未知"处理：可选、可试，而不是继续拦截
    }
    return r.State
}
```

**b. 非破坏化**：健康结论只用于**展示与排序**，不作为"能不能选"的否决权。

```go
// 反例：按采样结论把模型从列表里删掉
switch av[m.ID].State {
case StateUnavailable:
    continue            // ← 单次采样，凭什么否决？
}

// 正例：只保留"结构上不可用"的过滤（例如该模型走的根本不是聊天接口）
for _, m := range cat {
    if m.SystemOne {
        continue        // 结构性不可用，与采样无关
    }
    out = append(out, m)
}
```

**c. 多出口复核**：得出非"可用"结论后，换 2–3 个出口重测，任一成功即判可用。

```go
if r.State != StateAvailable {
    for try := 0; try < 3; try++ {
        rr := ProbeModel(withExit(ctx, pickNextExit(m.ID)), m)
        r = rr
        if rr.State == StateAvailable {
            break
        }
    }
}
```

**d. 用真实流量校正 + 保护窗口**（这条最有价值）

```go
const realOKWindow = 10 * time.Minute

// 真实请求成功时调用
func (l *Lane) NoteRealSuccess(model string) {
    now := time.Now().UnixMilli()
    l.mu.Lock()
    l.realOK[model] = now + realOKWindow.Milliseconds()
    prev := l.availability[model]
    changed := prev.State != StateAvailable || prev.At == 0
    if changed {
        l.availability[model] = ProbeResult{
            Model: model, State: StateAvailable, At: now,
            Detail: "实测可用（真实请求成功）",
        }
    }
    l.mu.Unlock()
    if changed {          // ← 见教训 6 的说明
        l.fireChange()
    }
}

func (l *Lane) protected(model string) bool {
    if until, ok := l.realOK[model]; ok {
        if time.Now().UnixMilli() < until {
            return true
        }
        delete(l.realOK, model)
    }
    return false
}
```

然后在健康检查落盘结论前，尊重保护窗口：

```go
// ⚠ 注意这一行必须在取锁【之前】算（见教训 6）
protected := r.State != StateAvailable && l.protected(m.ID)

l.mu.Lock()
if protected && l.availability[m.ID].State == StateAvailable {
    r = l.availability[m.ID]
    r.Detail = "实测可用（探测结论已忽略）"
}
l.availability[m.ID] = r
l.mu.Unlock()
```

**验证**：

```
1) 对 3 个标"不可用"的模型发真实请求   → 全部成功
2) 面板状态立即翻为                    → available
3) 触发重新检查，等 110 秒             → 仍然 available   ← 保护窗口挡住假限流
4) 原本被移除的模型                    → 重新出现在 /v1/models（9 → 10 个）
```

> **可迁移性**：**任何**健康检查/可用性系统都适用。核心命题是：
> **"观测系统不能只自证"** —— 你的健康检查本身也是一个会出错的观测者，
> 而真实业务流量是比它更可信的证据源。两者冲突时，应当让**真实流量赢，并给它一个保护期**。

### 教训 3 · Windows 子进程生命周期必须用 Job Object

**现象**：侧车进程反复崩溃重启，**单日 72 次**。日志里能看到：

```
FATAL start service: start inbound/socks[in-00]: listen tcp 127.0.0.1:21001:
      bind: Only one usage of each socket address ... is normally permitted
```

**根因（两个叠加）**：

1. **`Process.Kill()` 是异步的** —— 只发信号，不等进程真的退出。紧接着启动新实例时，端口可能还没释放。
2. **父进程死后子进程不被回收** —— 网关只在内存在持有子进程句柄。网关被强杀（任务管理器 / 崩溃 / `Stop-Process`）后，句柄丢失，子进程成为孤儿；下次启动时连 `Kill()` 都不会对它执行。

**修法（结构性，推荐）**：Windows **Job Object** + `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`。
把子进程绑进一个 job object，**父进程一退出（正常/崩溃/被强杀），系统自动把子进程一起收走**。

```go
//go:build windows

var killJob windows.Handle

func tieToParent(p *os.Process) error {
    if p == nil {
        return nil
    }
    if killJob == 0 {
        h, err := windows.CreateJobObject(nil, nil)
        if err != nil {
            return err
        }
        info := windows.JOBOBJECT_EXTENDED_LIMIT_INFORMATION{
            BasicLimitInformation: windows.JOBOBJECT_BASIC_LIMIT_INFORMATION{
                LimitFlags: windows.JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE,
            },
        }
        if _, err := windows.SetInformationJobObject(
            h, windows.JobObjectExtendedLimitInformation,
            uintptr(unsafe.Pointer(&info)), uint32(unsafe.Sizeof(info)),
        ); err != nil {
            windows.CloseHandle(h)
            return err
        }
        killJob = h
    }
    h, err := windows.OpenProcess(
        windows.PROCESS_SET_QUOTA|windows.PROCESS_TERMINATE, false, uint32(p.Pid))
    if err != nil {
        return err
    }
    defer windows.CloseHandle(h)
    return windows.AssignProcessToJobObject(killJob, h)
}
```

在 `cmd.Start()` 之后加一句 `_ = tieToParent(cmd.Process)` 即可（非 Windows 平台写成 no-op）。

**⚠ 一个必须知道的坑**：`killJob` 这个句柄**必须一直持有，绝不能提前 `CloseHandle`** ——
关闭句柄正是触发"杀掉全部子进程"的时机，那正是我们要的语义。提前关掉等于自己把侧车干掉。

**另加两层兜底**（防御性，成本很低）：

```go
// 启动前等端口真正空闲
func waitPortFree(port int, timeout time.Duration) {
    deadline := time.Now().Add(timeout)
    for {
        ln, err := net.Listen("tcp", fmt.Sprintf("127.0.0.1:%d", port))
        if err == nil {
            ln.Close()
            return
        }
        if time.Now().After(deadline) {
            return
        }
        time.Sleep(250 * time.Millisecond)
    }
}

// 端口仍被占用 → 说明有跨代孤儿，清掉
if portBusy(port) {
    sweepOrphan()          // taskkill /F /IM <sidecar>.exe
    waitPortFree(port, 5*time.Second)
}
```

**验证**：

```
强杀网关 → 侧车同时消失（孤儿进程 = 0）     ← Job Object 生效
再启动   → 崩溃循环 0 次
```

**修复后至今，日志里崩溃事件 0 次**（修前单日 72 次）。

> **可迁移性**：任何 Windows 上"主程序 + 侧车/子进程"的服务都该这么做。
> 注意 `AssignProcessToJobObject` 在"进程已在 job 里且不允许嵌套"时会失败 ——
> 忽略错误、退化为端口等待 + 清扫即可（**优雅降级比启动失败好**）。

### 教训 4 · 健康检查自身会成为故障源（控制面走了数据面）

**现象**：每次**冷启动**必然进入"全部请求 502"的死状态，且**无法自愈**。

**根因**：配置源跑在**本机**（`http://127.0.0.1:21000/...`），而控制器在刷新配置**之前**就已经把代理模式设为"轮询"。于是这个回环地址也被交给远端节点去拨号：

```
拉取配置失败
   → 侧车拿不到节点
   → 出口池为空
   → 所有请求 502
   → 刷新配置仍然走这条被劫持的链路 → 永远出不来
```

**修法（两处，任一单独都能缓解，建议都加）**：

```go
// 1) 回环地址一律直连，不交给代理
if host, _, err := net.SplitHostPort(addr); err == nil {
    if ip := net.ParseIP(host); (ip != nil && ip.IsLoopback()) || host == "localhost" {
        var d net.Dialer
        return d.DialContext(ctx, network, addr)
    }
}

// 2) 出口池为空时直连兜底（宁可走系统出口，也不要全线 502）
if r != nil {
    if c, derr := r.Dial(ctx, network, addr); derr == nil {
        return c, nil
    }
}
var d net.Dialer
return d.DialContext(ctx, network, addr)
```

> **可迁移性**：这是"**控制面依赖数据面**"的经典死锁。
> 自查方法：画出"谁启动谁"的顺序图，问一句
> **"为了让 A 工作，需要先让 B 工作；而 B 又依赖 A —— 有这种情况吗？"**
> 另一个常见变体：健康检查本身走被检查的通道。

### 教训 5 · 序列化层的 `omitempty` 会在下游变成"数据消失"

**现象**：网关把配置写进第三方客户端的配置文件，客户端启动时报 schema 校验错误，**全部模型消失**。

**根因**（Go → JSON → 跨语言 schema 的经典组合）：

```go
type ConfigRules struct {
    ProviderModelRules       []map[string]any `json:"providerModelRules,omitempty"`
    ManualProviderModelRules []map[string]any `json:"manualProviderModelRules,omitempty"`
}
```

当切片是 `nil`（未初始化）时，`omitempty` 会**直接省略这个 key**。而下游是严格 schema：

```
key 缺失 → schema 校验失败 → 客户端拿到空配置 → 模型列表为空
```

**修法**（两条一起）：

```go
// 1) 去掉 omitempty：这个字段是"必填空数组"，不是"可省略"
ManualProviderModelRules []map[string]any `json:"manualProviderModelRules"`

// 2) 显式初始化，别留 nil
ManualProviderModelRules: []map[string]any{},
```

**为什么难查**：症状在**下游**（客户端），根因在**上游**（一个 tag），中间隔着一次序列化。
而且"只是少了一个 key"看起来无害。

> **可迁移性**：任何"自己写 JSON 给别人的程序读"的场景。
> **规则：如果下游 schema 要求这个 key 存在，你的结构体就不该用 `omitempty`**。
> 反过来，`omitempty` 只应该用在"语义上确实可选"的字段上。

### 教训 6 · 并发状态：要么在锁内，要么在**取锁之前**算好

这条是我**自己引入**的 bug，被测试逼出来的，特别值得记。

**现象**：给"真实流量保护窗口"加逻辑后，健康检查在某些情况下会**整体卡死**。

**根因**：`sync.Mutex` **不可重入**。我把一个自己会取锁的函数，写在了已经持有该锁的临界区里：

```go
// ❌ 死锁
l.mu.Lock()
if r.State != StateAvailable && l.protected(m.ID) {   // protected() 内部又 l.mu.Lock()
    ...
}
l.mu.Unlock()

// ✅ 取锁前算
protected := r.State != StateAvailable && l.protected(m.ID)
l.mu.Lock()
if protected {
    ...
}
l.mu.Unlock()
```

**为什么它可能"偶尔才发作"**：Go 的 `&&` **短路求值**。如果 `r.State == StateAvailable`，
右边根本不会被求值 —— 于是**只有"检查得出非可用结论"这条最常见路径才会踩中**。

**同一条教训的第二个实例（性能型）**：把一个"每次成功都要调用"的函数写成无条件广播：

```go
// ❌ 每个成功请求都触发一次面板重建
l.mu.Unlock()
l.fireChange()

// ✅ 只在状态真的翻转时广播
l.mu.Unlock()
if changed {
    l.fireChange()
}
```

> **可迁移性**：写任何 `RWMutex` 代码时，养成两个习惯：
> 1. **先问"这个函数自己取锁吗"**，是就把它挪到临界区外；
> 2. **热点路径上的"通知/广播"要有条件**，否则会把 O(1) 的更新放大成 O(配置源者)。

### 教训 7 · 证伪比证明便宜：一个"解释"不等于"机制"

**现象**：客户端**非流式**请求 100% 失败（0/8，全 429），而同模型**流式**请求 100% 成功（8/8）。
**顺序反过来也一样**（先流式后非流式 → 8/8 然后 0/8），排除了"预热/顺序"因素。

**我们做对的一步**：没有停在"那就是流式的问题"，而是**去证伪"请求本身不同"这个假设**。

做法：把网关的上游地址编译期指向一个**本地捕获服务**，打印请求的头和体。

**结果**：两条路径发出的请求 **逐字节相同** ——

```
=== headers 差异 ===
  (无)
=== body 差异 ===
完全相同: true
```
（连同 `x-session-*`、`x-request-*`、`authorization`、`user-agent` 全部一致）

**结论**：机制在网关内部，且**客户端侧不可观测**。这一条我们**如实记为未定位**，没有编一个听起来合理的解释。

> **可迁移性（本文最重要的一条方法论）**：
> 当你遇到"**看起来一样、行为不同**"，第一步永远是**先把"一样"证死或证伪**，
> 而不是先猜机制。抓包 diff 的成本很低，但它能立刻砍掉一大片假设空间。
>
> 而且：**"找到一个解释"和"找到了机制"是两件事**。前者让人舒服，后者才有用。

## 3. 调试方法论（可直接复用的四件）

### 3.1 抓包 diff：证伪"输入相同"的最快手段

把不可观测的第三方换成**自己的捕获服务**，是最直接的观测手段：

```go
// 上游地址做成 var，便于用 ldflags 覆盖（生产默认值不变）
var UpstreamBase = "https://real-upstream.example"

// 调试构建
go build -ldflags "-X pkg/lane.UpstreamBase=http://127.0.0.1:9999" -o debug.exe ./cmd/...
```

捕获服务把 **方法 / URL / 全部请求头 / 完整 body** 写成 JSONL，然后逐字段 diff。

**要点**：
- **用调试专用构建，别动生产实例**（我在这一点上犯过错，见 §3.4）
- 捕获服务要能**返回合法的最小响应**，让被测系统走完正常路径（否则它会在重试逻辑里打转，你就看不到想看的请求）

### 3.2 race detector 在 Windows 上要额外准备

`go test -race` 在 Windows 上**需要 cgo + gcc**：

```powershell
# 装一个 MinGW（winget 即可）
winget install -e --id BrechtSanders.WinLibs.POSIX.UCRT

$env:PATH = "<mingw>\bin;$env:PATH"
$env:CGO_ENABLED = "1"
go test -race ./...
```

**为什么值得**：本次新增的并发状态（一个受保护的 map + 一个封禁账本）**被工具验证为零竞态**，
这比"我人工看了一遍，应该没问题"强得多 —— 后者只是推断，前者是证明。

### 3.3 日志时间分桶：判断"修复到底生效没有"

**别只看"有多少次错误"，要看"错误在时间轴上的分布"。**

```
崩溃/重启事件按 10 分钟分桶：
  02:00   6 次
  03:00  25 次   ← 修复前
  03:30  22 次
  03:40  10 次
  03:50  16 次   ← 最后一次 03:55:58
  04:20   1 次
  04:40   1 次   ← 最后一次 04:42:02
  ─────────────
  05:00   0 条   ✅ 修复后彻底停止
```

这一个图同时回答了两个问题：**修复前有多糟**（72 次）和**修复是否真的生效**（之后 0 次）。
比"我改了，应该好了"可信得多。

### 3.4 反面教材：调试时不要停生产实例

我为了跑抓包版停掉了生产网关，结果**连带把看门狗和配置服务也停了**，服务中断数分钟。

**正确做法**：调试构建**另起端口、另用数据目录**（`ZEN_GATE_HOME` 之类），完全并行。

### 3.5 反编造门：主动撤回自己的错误结论

本次有两条"发现"在复测后被我自己撤回：

| 我的声称 | 复测结果 |
|---|---|
| "管理接口不校验 Origin" | **错**。Origin 只对写操作检查，我测的是读操作。重测写操作 → **403 被拒**，控制有效 |
| "额度是全局共享池" | **错**。实测按出口 IP 计：20 个出口里只有 6 个当时有额度；同出口连打 6 次全成功 |

**规矩**：**没有可复现证据路径的声称不是发现，是噪音。** 撤回不是丢脸，是纪律。

## 4. 一份"未定位"的诚实记录

留下这一节，是为了说明**边界在哪**。

**未定位项**：客户端非流式 0/8、流式 8/8，**上游请求已证明逐字节相同**，机制未找到。

**它为什么留着**：
1. 这是**一次真实的未解**，不是"待办"；编一个解释会让整篇文档的可信度下降；
2. 它恰好是**教训 7 的实例**：证伪掉了最强的假设（"请求不同"），剩下的空间还没探索；
3. 它对实际使用**影响有限**：所有主流编程 Agent 默认都走流式。

**结论句**：**"证伪到这一步"本身就是产出**。

## 5. 检查清单（对照自己的网关）

给同类的"本地网关 + 多出口 + 池化上游"系统，逐条自查：

**出口层**
- [ ] 轮换是否**真的**逐请求生效？（打日志比对"选中出口"与"实际出站连接"）
- [ ] 连接池/keep-alive 是否架空了 `DialContext`？
- [ ] 出口失败后是否**换个出口重试**，而不是直接判定资源不可用？
- [ ] 同一资源在"某个出口不可用"和"全局不可用"之间有没有区分？

**健康判定层**
- [ ] 健康结论有**有效期**吗？
- [ ] 结论会**破坏性地**影响可用集合吗？（删除 vs 降权）
- [ ] 单点采样会不会被当成全局事实？有没有**多采样复核**？
- [ ] **真实业务流量能不能覆盖健康结论**？有没有保护窗口？
- [ ] 面板/状态展示与**实际能力**的一致性有没有被验证过？

**进程生命周期层**
- [ ] 子进程在父进程被**强杀**后会被回收吗？
- [ ] `Kill()` 之后有没有等端口/资源真正释放？
- [ ] 有没有"上一代遗留进程"导致启动失败的兜底？

**配置/序列化层**
- [ ] 写给他人的 JSON，**必填字段有没有误用 `omitempty`**？
- [ ] 切片/映射有没有显式初始化（避免 nil）？

**控制流层**
- [ ] 控制面（拉配置/健康检查）会不会依赖数据面（被代理的通道）？
- [ ] 有没有"为了让 A 工作必须先让 B 工作，而 B 又依赖 A"的环？

**并发层**
- [ ] 临界区里调用的函数**自己会不会取同一把锁**？
- [ ] 热点路径上的"通知/广播"有**条件**吗？

**验证纪律**
- [ ] `go vet` / `go test` / `go test -race` 三件套跑过吗？
- [ ] 修复后用**时间分桶**确认过"真的停了"，而不是"应该好了"？
- [ ] 有没有留一份**未定位项**的诚实记录？

## 7. 一句话总结

**这 35 处修复里，真正值钱的不是"修好了什么"，而是三类可迁移的认识：**

1. **复用会悄悄吃掉你以为在做的事**（连接池 vs 轮换）；
2. **观测系统也是会出错的观测者，真实流量应当有更高权重**（健康判定）；
3. **进程/资源生命周期要显式设计，不能指望"父进程死了子进程自然会跟着走"**（Job Object）。

**以及一条方法论**：**先证伪"输入相同"，再谈"为什么行为不同"。**
