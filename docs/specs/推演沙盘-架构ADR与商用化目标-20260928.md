### evidence 层重新评价（本轮最重要的发现）

这是**把认识论编码成可复用领域语言**的尝试，7 个模块各司其职且互不重叠：

| 模块 | 行数 | 职责 | 评价 |
|---|---|---|---|
| `baseRate.js` | 289 | 基率是唯一合法先验；p/n/k 汇总 | 核心 |
| `dueBranches.js` | 87 | 到期口径的分支判定 | 修过「静默饿死 31 条」真缺陷 |
| `labBoundary.js` | 87 | **实验场/真实对局边界**（09-27 新增） | ★★★ |
| `revealClass.js` | 89 | **揭晓分流** auto_ok/need_human/stuck（09-28 新增） | ★★★ |
| `truthBasis.js` | 56 | 真值口径排除 | — |
| `domain.js` | 50 | 域归类 | — |
| `seriesKey.js` | 31 | 序列标识 | — |

**labBoundary.js 为什么漂亮**（全评审中我给出的最高单项设计分）：
- 解决的问题：真实对局的题与模拟局/语料局的题混在同一本账里，导致**「预测能力」的分母被污染**，而真实局没有可复核的真值锚。
- 判定口径写死：games.source 已知取值则权威（basis=source）；未知则回退 game_type 前缀（basis=game_type）并**如实标注**。
- **白名单式而非黑名单式**：新增游戏类型默认落真实局（保守）。
- **「取拒收需确凿证据，禁把没登记当是真实局」** —— 反 Goodhart。
- 纯函数、不做网络、不写任何表。

**revealClass.js 为什么漂亮**：
- 把「到期未解」分成 auto_ok / need_human / stuck 三类，**互斥且完备**（有测试证）。
- **分类依据是 kind 的取数能力（固有属性、可复现），不是运行时日志** —— 守护进程的 pending/fetch-fail 只存在于运行时、没落库、不可查。
- **「为什么 stuck 不做成可点的按钮：点了没反应比不给按钮更糟」** —— 产品判断被写进代码注释。

**问题**：这一层**没有自己的 HTTP 端点**。价值全部被锁在进程内。（见 ADR-003）

## ADR-001：商用目标形态选哪一档

**Status**：Proposed
**Deciders**：创始人 + 任何潜在投资人

### Context

**约束（先说死，它们决定答案）**：
- 团队 = 1 人 + AI 代理，16 天，413 commits。**没有第二个工程师。**
- 已投入 62,618 行代码 + 94,660 行文档，**沉没成本极大**。
- 用户 = 1（作者本人），收入 = 0，PMF 证据 = 0。
- 外部市场：B2C 需求被三条独立证据证伪（GJ Open 70 人 / 15+ 同构项目 0–2 star / 无任何已验证付费先例）。
- 唯一有真实付款方的方向是 B2B，形态是服务不是软件，年天花板 = 创始人产能 75–240 万。
- 代码当前绑死单机：SQLite 单文件、0.0.0.0:8787、无鉴权、无 CI、无容器、无异地备份。

**要解决的问题**：从「一台研究者的机器」到「可投入真正商用」，走哪条路。

### Options Considered

#### Option A：做成多租户 SaaS（Postgres + 容器 + CI + 鉴权 + 计费 + 多租户隔离）

| 维度 | 评估 |
|---|---|
| 复杂度 | **极高**。SQLite→Postgres 迁移、schema 重写、事务语义变化、并发模型重做 |
| 成本 | 基建 85–160 人日 + 12 个月真前瞻数据 + 招 2–3 人 = **300–500 万** |
| 可扩展性 | 好（但需求未被验证，扩的是不存在的东西） |
| 团队匹配度 | **极差**。单人无法在 6 个月内同时运维 SaaS 与跑数据 |
| **致命问题** | **在 PMF 证据为零时先烧 500 万。** 且上一份报告已判定：这个品类没有可规模化市场 |

**Pros**：理论上唯一能支撑 VC 回报的形态。
**Cons**：市场不存在；投入产出比是本次评审中最差的一个选项。

#### Option B：单机优先 + 契约层对外化（推荐）

| 维度 | 评估 |
|---|---|
| 复杂度 | **中低**。不换数据库、不做多租户；只做鉴权 + 任务持久化 + CI + 契约层 HTTP 面 |
| 成本 | **30–80 万 / 12–18 个月**（1 人全职 + 1 兼职 + 差旅 + 少量 API） |
| 可扩展性 | 够用。目标并发 < 50 QPS；SQLite WAL 在此规模无问题 |
| 团队匹配度 | **好**。全部工作可在单人 90 天内完成 |
| 商业形态 | B2B 方法论服务；工具是「交付载体 + 案例素材」，不是商品 |

**Pros**：与团队规模匹配；不需要烧钱验证已知不存在的市场；把唯一稀缺资产（evidence 契约层）推到能卖的位置；每一分投入都同时服务于「交付案例」。
**Cons**：年天花板锁死；不构成 VC 生意；需要创始人接受「这是咨询生意不是产品生意」。

#### Option C：开源 + 个人品牌，靠影响力变现

| 维度 | 评估 |
|---|---|
| 复杂度 | **低**。整理文档、剥掉密钥、修 P0、开源 |
| 成本 | **10–20 万 / 6 个月** |
| 可扩展性 | 不适用 |
| 团队匹配度 | **极好** |
| 商业形态 | 赞助 / 咨询转化 / 招聘漏斗 |

**Pros**：成本最低；负结果账本这类资产在开源社区的稀缺性远高于在闭源 SaaS；15 个 0–2 star 的克隆说明**这个位置还没有被占据**。
**Cons**：需要持续内容产出；变现周期 6–12 个月；几乎无防御性。

### Trade-off Analysis

三个选项不是互斥的，正确答案是 **C → B 的顺序**：
1. **先 C 后 B**。开源 + 修 P0 + 契约层对外，成本 10–20 万，同时产出**可公开的案例研究**（Good Judgment 模式的核心资产）。
2. 开源带来的外部反馈与审计，正好检验 evidence 契约层在没有作者的情况下是否还成立 —— **这是对「方法论能否脱离创始人独立运转」的唯一直接检验**。
3. 若 B2B 有付费，转 B（加鉴权 + 任务持久化 + 契约层限流）；若没有，保持 C，不追加投入。

**明确否决 Option A。** 理由不是「贵」，是**它把资源配置在一个已被证伪的市场上**。

### Consequences

- **更容易**：单人可控；每一分钱都在验证假设而不是在建设产能。
- **更难**：必须接受「公司估值约等于 0」这个现实；如果要 VC 回报，本项目不是标的。
- **需要重新审视**：若 12 个月内拿到 3 个付费 PoC 且都需要多租户，届时再评估 Option A。

### Action Items

1. [ ] 修两个 P0（密钥清史 + SSRF 白名单）—— **48 小时内，不可协商**
2. [ ] 剥掉内网耦合：0.0.0.0 改为显式 HOST 配置 + 加共享令牌（0.5 人日）
3. [ ] 建 GitHub Actions + 前端 npm test script（1 人日）
4. [ ] 决策：先 C（开源）还是先 B（B2B 交付）—— 建议 C，2 周内定
5. [ ] 把 evidence 契约层升格为对外 API（见 ADR-003）

## ADR-002：账本改成 append-only 事件流

**Status**：Proposed
**优先级**：P1（这是本次评估中**投入产出比最高**的一条）

### Context

**当前实现（实测）**：`db/predictionsStore.js` 中有**三处 UPDATE**：
- :356 `UPDATE predictions SET resolved_at=..., outcome=?, resolve_note=? WHERE id=?`
- :499 `UPDATE predictions SET <audit columns> WHERE id=?`
- :519 `UPDATE predictions SET tautology=? WHERE id=?`

409 不可变守卫**只在 resolve 时拦截**。所以「账本不可变」的实际语义是「**结算结果**不可改 + 其余字段可改」。

**由此产生的三个问题**：
1. **闭环第 4 环断裂**：项目自己的 design 文档承认 —— 409 文案把人引向「另开修正记录」，但全库 grep amend **零命中**。用户无法修正自己的判断，系统因此永远不会从错误中改进。
2. **自相矛盾**：为了不改账本只能「另开一条」，但那条没有数据模型。
3. **对外表述不成立**：对外宣称「账本不可变」，实际可 UPDATE 审计字段与 tautology 标记。**这是一次可能被外部质询击穿的说法。**

**关键发现 —— 项目已经做对过一次**：
`db/verdictsStore.js` **就是真正的 append-only**：判词全量逐行落库（3 prompt 变体 × 3 温度 = 9 行/题），用 run_id 做批次隔离，UNIQUE 索引用 `COALESCE(run_id,'')` 表达式索引表达「同题多批次可并存」；并且 model（编排器声明的批次标签，配对键，**不得改动**）与 resolved_model（事实层，回答「这行到底是谁生成的」）**两列并存 = 声明与事实分离**。

> 该文件注释原文记录了这条设计的由来：「2026-09-14 实测发现 model 列只是编排器写死的标签，与真正生效的 provider/model 脱钩 ⇒ 换供应商后行标签不变、无法验收。」

**这是一个成熟的 provenance 设计，业界很多系统做不到。它已经在这个项目里了。**

### Decision

**把 predictions 从「可变行 + 409 守卫」改为「append-only 事件流 + 物化视图」，做法照抄 verdictsStore 已被验证的模式。**

事件类型（每条带 event_id / supersedes / run_id / occurred_at / actor）：

| 事件 | 载荷 | 语义 |
|---|---|---|
| question_asked | statement, kind, cutoff, layer | 用户提出一道题 |
| probability_set | prob, by(user 或 engine) | 设概率；**引擎与用户分开记** |
| truth_resolved | outcome, source, basis | 结算真值 |
| probability_superseded | new_prob, reason | **修正 = 追加一条新概率，天然不改历史** |
| score_recorded | brier, skill | 计分 |
| excluded | reason | 口径排除 |

物化视图 predictions_current：每题取最新 probability_set（用户优先于引擎）与 truth_resolved，供现有全部报表与前端使用。

### Options Considered

| 方案 | 复杂度 | 保留「不可变」？ | 解决修正闭环？ | 评价 |
|---|---|---|---|---|
| **A. 事件流 + 物化视图**（推荐） | 中（8–12 人日，含迁移与回放测试） | 是，真正不可变 | 是，修正 = 追加 | 与 verdictsStore 同构，风险已知 |
| B. 保留 409 + 加 amend 表 | 低（2 人日） | 部分修补 | 半修 | 治标；amend 表就是「另开修正记录」的数据化，但没解决统计口径 |
| C. 允许原地改 + 审计日志 | 低 | 否 | 是 | 直接放弃唯一有价值的架构属性 |

### Trade-off Analysis

选 A 牺牲的是「简单」：多一个事件表、多一个物化视图、报表 SQL 要改（现有 stage4-run / g2-report / calibration-report 的口径都直接读 predictions）。
选 B/C 牺牲的是「诚实」：一个对外宣称「账本不可变」但实际有 3 处 UPDATE 的系统，**在一次外部尽调中就会被拆穿** —— 而这正是这个项目唯一的品牌资产。

**选 A。** 理由：这个项目唯一在市场上稀缺的东西是「可被审计的诚实」，为了省 10 个人日去保留一个不成立的承诺，是本末倒置。

### Consequences

- **更容易**：修正闭环成立；「不可变」名副其实；用户可以改主意而历史完整保留（这是正确的产品行为，也是 Brier 校准的诚实要求 —— 强迫用户不能改判断会污染数据）。
- **更难**：所有读侧要迁移；需要写事件回放与一致性校验测试。
- **需要重新审视**：用户改概率后，其历史 Brier 该记「原始」还是「最终」？**建议两者都记**（probability_set 全部参与计分，且报表面板展示「改过 n 次」）。这也是一个有话可讲的设计选择。

### Action Items

1. [ ] 设计 ledger_events 表 DDL（照 verdictsStore 的 additive 迁移范式）
2. [ ] 写 event_replay.cjs：events → predictions_current 视图物化器，带 sha256 自证
3. [ ] 迁移 1,994 条历史行为 question_asked + probability_set + truth_resolved 三事件组（1 人日，含 dry-run 演练）
4. [ ] 读侧切换 + 口径对齐测试（现有金样 diff 必须为 0）
5. [ ] amend 端点实现：POST /api/predictions/:id/supersede → 追加 probability_superseded

## ADR-003：把 evidence 升格为「预测契约层」并对外化

**Status**：Proposed
**优先级**：P0（成本最低、差异化最高的一条）

### Context

evidence 层 7 个模块是这个项目**唯一无法被 3 个月复制的部分**（另一块是 PREREG/anchor-gate 纪律，但那是脚本不是库）。
它做的事是：**给定「题面 + cutoff + 真值锚」，判定这道题是否配进账本、配进哪一层、到期去哪里查、会不会泄漏。**

这在国际上没有直接对应物。closest analog：
- dbt tests / Great Expectations / Evidently AI → **数据质量**契约
- 本项目 → **可证伪性质量**契约

**但它现在没有 HTTP 端点。** 消费方只有自己的前端和 121 个脚本。**全部价值被锁在进程内。**

外部证据显示这是一个**真实的空白位**：
- 15+ 个 GitHub 同构实现（brierly / lucid / hunchlog / decision-log / calibration-log…）**全部 0–2 star** —— 它们做了记录和计分，**没有一个做「这道题配不配」的判定**。
- Metaculus 的题目由社区人工裁决（作者自己写过对比：「LLM 自动生成+结算的可验证率 96%，exceeding the rate of Metaculus」）。
- B2B 侧 NetSet Software 卖的是企业内部预测**市场**（造题、下注、结算），**不是造题资格审计**。

### Decision

**新增一个只读的对外端点族，把 evidence 变成一等 API：**

- `POST /v1/contract/validate`
  入参：`{ statement, cutoff, anchor_kind, options }`
  出参：`{ admissible, reject_reason, layer, due_at, reveal_class, anchor_reachability, leak_risk, engine, method_version }`
- `GET /v1/kinds` → 52 个锚的机器可读目录（label / group / 域 / 商用许可 / 成本 / 存活状态）
- `GET /v1/kinds/:kind` → 该锚的判据、到期口径、已登记缺陷
- `POST /v1/audit` → 批量审计一批题面，返回拒绝清单 + 原因分布
- `GET /v1/contract/version` → 契约版本（semver；改动 = 版本递进，照 PREREG 惯例）

**三条硬规则**（照搬项目已有纪律，不新造）：
1. 只读，绝不写账本（沿用 leak-scan 的零写库锁思路）。
2. method_version 必须随响应返回 —— **口径变更必须可追溯**。
3. 「未覆盖必须显式计数」—— 无法判定的锚返回 unverifiable 而非 pass。**这是本项目最有价值的一条纪律，必须进入对外契约。**

### Options Considered

| 方案 | 复杂度 | 差异化 | 评价 |
|---|---|---|---|
| **A. 契约层对外化 + 开源**（推荐） | 低（3 人日） | 高（国际无对应物） | 成本最低、差异化最高 |
| B. 只做内部，不对外 | 0 | 0 | 保持现状，价值锁死 |
| C. 整包开源（含 scripts 与账本） | 中 | 中 | 会暴露 1,994 条演示数据与 450 条 sim 污染，反而损伤「诚实」品牌 |

### Trade-off Analysis

- 得到：一个可被第三方集成的、可定价的、可开源获客的能力；也是「我们测了什么、什么没成立」这句话的**可执行形态**。
- 失去：完全没必要失去。这一层是纯函数，加 HTTP 门面不影响内部任何路径。
- 风险：对外暴露后，labBoundary 的判定口径会成为事实标准，**改起来要版本递进** —— 这正是 PREREG 制度的价值，但也意味着**不要在口径还不稳时就对外**。

### Consequences

- **更容易**：把「卖方法论」变成「卖一个有名字的东西」；开源社区可以直接调用，这解决了 B2C「没有日常使用钩子」的根本问题 —— **钩子变成「别人调你的 API」**。
- **更难**：口径稳定性责任；需要对外契约的版本策略与变更公告。
- **需要重新审视**：是否开源这一层？**建议开源**（获客），把 52 个锚的**私有扩展**（如赔率类）留作增值。

## ADR-004：脚本层与运行时层物理隔离 + gate 数据层强制

**Status**：Proposed
**优先级**：P0

### Context

**事实**：`scripts/` 24,831 行 / 121 顶层 + 62 archive + 16 分片，**直接写 p1a.db**，绕过 routes 的全部校验、全部 gate、全部口径检查。
**后果已经发生**：
- `gate='scored'` **0 行**，而 `gate='descriptive'` 的 1,935 行**全部带 assigned_prob** —— 因为 CHECK 只管 0..1，不管 gate。铁律「概率只在 scored 后出现」**在一个 HTTP 入口生效，批处理管线完全绕过**。
- `intake_rejects` **0 行**、intake_questions 2 行 —— 拒收门在生产从未留痕。
- `scripts-require-safety.test.cjs` 记录了一次真实数据损失事故：「每跑一次测试就往 sim/out 写同名件；2026-09-16 终态归档提交后 1 秒即覆盖了同名 tracked 产物」。

**这是一个架构问题，不是纪律问题。纪律已经被证明压不住。**

### Decision

**三层写路径分离，且用 SQLite 层强制，而不是靠约定：**

1. **`src/ledger/` —— 唯一生产写路径**。所有写操作经 LedgerWriter 单一入口，内含：gate 校验、cutoff 校验、dueOf 校验、写后 sha256 自证。
2. **scripts 全部改为调用一个 CLI 门面**（p1b/cli 已存在，扩它），脚本本身只做编排，不碰 DB。
3. **数据层强制**：
   - 建 CHECK 约束或 BEFORE INSERT 触发器：gate='scored' 之外的行**不得有非 NULL assigned_prob**。若业务上必须允许，改成 assigned_prob_source 列，值域 user / engine / backfill，且 engine 需配 engine_ref 指向 stage4-run 的金样 sha。
   - intake_rejects 与 intake_questions 改为**每次分类必写一行**（包括放行的），使「过锚率 / 拒绝率」成为可查量而不是事后推算。

### Options Considered

| 方案 | 复杂度 | gate 是否真生效 | 评价 |
|---|---|---|---|
| **A. 单一写路径 + DB 触发器 + CI 断言**（推荐） | 中（11–15 人日） | 是 | 一次解决，已发生的三个问题全部封死 |
| B. 只加文档规范 | 极低 | 否 | 已证明压不住（121 脚本已绕过 16 天） |
| C. 把 scripts 全删掉重写 | 高（30+ 人日） | 是 | 得不偿失；多数脚本是一次性研究件，删了会丢失可复现性 |

### Trade-off Analysis

- 得到：**所有对外声明第一次成为事实**。「拒收门在生产生效」「gate 在数据层强制」这两句话将不再需要「目前 0 行」的免责语。
- 失去：121 个脚本要改。大部分是机械替换 —— **预计 6–10 人日，不是 20–40**，因为不需要建 CLI 框架，只需要一条 require 纪律 + CI 检查。
- 风险：改写脚本时可能引入静默行为变化。**对策**：迁移前后对 predictions 全列 dump sha256 比对（项目已有此先例，`vault-sync.cjs:41-46`）。

### Consequences

- **更容易**：数据可信度从「靠人守」变成「靠 schema 守」。
- **更难**：写库路径收窄后，早期那些「图快直接 INSERT」的批处理会变慢。
- **需要重新审视**：archive 里的 62 个脚本是否还需要保留可运行性？**建议只保留 sha256 + 产出件，不保留可执行**。

### Action Items

1. [ ] 建 `src/ledger/` + LedgerWriter（3 人日）
2. [ ] 加 CHECK / 触发器（1 人日）
3. [ ] **加 CI 检查：scripts 中出现 INSERT / UPDATE / DELETE / conn.exec 即构建失败（0.5 人日 —— 本 ADR 里杠杆最高的一条）**
4. [ ] 121 脚本批量迁移（6–10 人日，分批，每批跑金样 diff=0）
5. [ ] intake 改为每分类必写（1 人日）

## ADR-005：图表层与依赖策略

**Status**：Proposed
**优先级**：P2

### Context

前端自研 14 个图表原语（Gauge / HeatGrid / ForestPlot / Bars / LineChart / Waffle / SpecimenStrip / BiasStrip / DeviationBar / ErrorBar / ReadoutCard / ChartFrame / Controls / scale），**零图表库依赖**。

**动机是对的**：攻击面小、包体可控、视觉完全可控，且 `palette-single-source.test.mjs` + `tokens.css` 单一令牌真源 + 20 条防复发闸构成了一个纪律良好的小型设计系统。**有意识、可测试、无污染。**

**但代价被低估了**：
- 无障碍：图表没有等价的 data table 视图（键盘 / 读屏用户拿不到数据）
- 可导出：无法导出图 / 数
- 国际化：数字与日期格式写死
- 维护：14 个原语 × 4 档断点 = 测试矩阵很大

而 charts.test.mjs / a11y.test.mjs 的存在说明作者**已经意识到**这个问题，但只做了「组件行为」测试，没做「等价表格」。

### Decision

**保留自研（不引入图表库），但补一条硬规则：每个图表原语必须提供 asTable 等价视图，且 dist 产物必须包含它。**

理由：引入 Recharts / ECharts 会带来 300KB+ 依赖、破坏单一令牌真源，且**不解决**「无障碍等价表格」这个真正的需求（那些库也要自己写）。**自研 + 强制等价表格 = 同样的可访问性，不牺牲令牌真源。**

### Action Items

1. [ ] ChartFrame 增加 renderAsTable 开关 + 每个原语实现 asTable（4 人日）
2. [ ] dist 扫描断言：每个 chart 导出必须配 asTable（0.5 人日）
3. [ ] 删 8 个死页面 2,524 行，把禁词扫描改为扫 dist 产物（0.5 人日）

## 最后：这些 ADR 解决不了什么

必须说清楚，否则这份文档会被误读为「照做就能商用」：

1. **它不创造需求。** /v1/contract/validate 是本项目**唯一有差异化且成本低（3 人日）**的对外能力，但上一份报告的判定没有变：这个品类没有可规模化的 B2C 市场。契约层开源能带来关注与集成，**不带来付费预测**。
2. **它不解决 Bus Factor = 1。** 60–71 人日对一个人是 3–4 个月，这 3–4 个月里他不能同时获客。**必须先决定 C（开源获客）还是 B（B2B 交付），不能两个都做。**
3. **它不改变「预测能力实测为零」这个事实。** 工程做得再干净，assigned_prob 等于 baseRate 依然成立。ADR-002 改的是**记录的可信度**，不是**预测的能力**。这两件事在对外表述上必须严格分开。
4. **它不改变评分。** 本 ADR 集把技术分从 5.0 提升到可到 6.0–6.5（若全部完成且有外部验证），但市场 1.0 与商业 0.5 不会被架构改进移动。**加权总分仍在 2.5–3.0 区间。**

> 一句话：这份 ADR 回答的是「如果要商用，最短路径是什么」，
> 不回答「值不值得商用」。后者上一份报告已经回答了：**先证明有人付钱，再做这些。**
