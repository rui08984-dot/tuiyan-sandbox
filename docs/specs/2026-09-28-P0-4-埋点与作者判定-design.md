## 1. ★作者 vs 非作者：怎么判定

### 1.1 判定规则（唯一一条，没有第二条）

> **本次请求出示的密钥与服务端 `P1B_AUTHOR_KEY` 做 `crypto.timingSafeEqual` 常量时间比较：
> 相符 ⇒ `actor = 'author'`；不符或未出示 ⇒ `actor = 'visitor'`。**

- 密钥出处：环境变量 `P1B_AUTHOR_KEY`，**只从 env 读**，不落盘、不入库、不进日志、不回响应。
- 出示方式二选一：请求体 `author_key`，或 header `x-p1b-author-key`。
- 前端粘一次即可：`localStorage.setItem('p1b_author_key', '<与服务端相同的值>')`
  （`WhereOffPage.tsx` 每次请求都带上；没粘就不发这个字段）。
- 落库的只有**判定结果**（`actor`）与**判定依据**（`actor_proof` 枚举：
  `key_match` / `key_mismatch` / `no_key_presented` / `no_server_key`），
  **密钥原文一个字节都不入库**（测试里有反证：三张表扫不到密钥原文）。
- 长度不同直接判不符——长度本身不是秘密；这是常量时间比较的标准做法。
- `actor_proof` 列带 CHECK 约束 `actor<>'author' OR actor_proof='key_match'`：
  **结构上锁死**「作者行只能由密钥命中产生」，杜绝别处代码手写 author 混进来。

### 1.2 为什么是密钥而不是别的信号（三个被否掉的方案）

| 候选 | 否掉的理由 |
|---|---|
| 按 IP 判（`127.0.0.1` ＝ 作者） | ① **隐私硬约束直接否掉**：IP 是个人信息，本件承诺一列都不记；② 作者本人会用手机走局域网地址进来，判不出来。 |
| 按「是不是本机 `node` 进程发的」判 | 浏览器请求永远不是本机进程发的 ⇒ 作者本人必然被判成访客。 |
| 让前端自报 `is_author=true` | 谁都能自报 ⇒ 外部访客一句话就把自己摘出去了，计数失去意义。 |

共享密钥是**只有作者知道的东西**——这是唯一一个「作者本人有、外部访客没有」的判据。

### 1.3 它防什么、不防什么（如实说清）

- **防**：把作者本人的使用混进外部访客的计数（作者天天点，PMF 数会被自己的使用量冲垮）。
- **不防**：有意冒充——知道密钥的人可以冒充作者。但 P1B-SPEC §6 本就明令
  「局域网可信网不做鉴权」，且知道密钥的人本来就能直接改库。这是一枚**分隔符**，不是身份认证。

### 1.4 fail-closed：没配密钥时谁也判不出作者

`P1B_AUTHOR_KEY` 没设 ⇒ **任何人**（哪怕出示了正确的密钥）都判成 `visitor`，
`actor_proof='no_server_key'`，且 `GET /api/analytics/summary` 会：

- 回报 `author_key_configured: false`；
- 在 `warnings[]` 里明写「服务端未配 P1B_AUTHOR_KEY ⇒ 谁也判不出作者」。

**方向很重要**：把作者误记成访客，只是让数变脏；把访客误记成作者，
会直接毁掉 PMF 判断（分母被污染）。两个方向的错，后者重得多，所以一律偏向前者。
宁可少一个桶，也不给一个看起来能用的错数。

### 1.5 身份归属的两层切分

| 标识 | 谁铸造 | 为什么 |
|---|---|---|
| `visitor_id` | **服务端**（`v_` + 32 hex，`crypto.randomBytes`） | 客户端带来的陌生 id **不认**，改为重发新 id 并回报 `visitor_reissued:true`——身份只能由服务端铸造，前端无法凭空造一个「老访客」来污染计数。 |
| `session_id` | **客户端**（也可由服务端兜底发） | 它只是幂等去重用的关联键，不承载身份；客户端自己持有才能在重试/双挂载时对上同一行。 |

访客行一旦被判为 author 就**只升不降**（偶发的一次误判不该把作者永久打成访客）。

## 2. ★隐私硬约束

> **只记事件与计数。绝不记题面内容，绝不记任何个人信息。**

这一条是**结构性的**，不是靠自觉：

1. 三张表**没有** `statement / text / title / content / ip / user_agent / ua / referer / email /
   name / author_key / key / token / phone` 任何一列。
2. 路由层**从不 spread 请求体**：每个入参都从白名单逐个取值，取不到的键直接丢弃。
   ⇒ 「把题面顺手塞进请求里」在结构上落不了库；且**多余字段不报错**（返回 200），
   免得前端因为带了多余字段而断掉埋点。
3. 题目只以 `subject_id`（整数主键）出现：**可计数、不可阅读**。
   要看题面请走题库自己的端点，埋点不复制题面。
4. 访客 id 与任何真实身份无映射关系，它只是让「同一个人」在多次会话间可被认出。

**反证测试**（`p1b/test/analytics-telemetry.test.cjs`）：请求里夹带题面、邮箱、IP、UA、Referer，
落库后三张表全量 dump —— 一个字都扫不到。

## 3. 三张表（additive · 幂等）

照 `p1b/src/db/` 既有范式（`intakeStore` / `verdictsStore` / `predictionsStore`）：
共享库禁 DDL ⇒ **p1b 私有表**，启动/注册时 `CREATE TABLE IF NOT EXISTS`，
不改 p1a 任何既有表、不改任何既有列语义。全部 `IF NOT EXISTS` ⇒ 重复 `ensure` 零副作用
（测试里连跑三次，列形状完全不变）。

| 表 | 主键 | 记什么 |
|---|---|---|
| `analytics_visitors` | `visitor_id`（服务端发） | `actor` / `actor_proof` / 首见末见时刻 / 会话数 |
| `analytics_sessions` | `session_id`（客户端关联键） | `visitor_id` / `actor` / `started_at` / `ended_at` / `end_reason` |
| `analytics_events` | `id` | `event` / `visitor_id` / `session_id` / `actor` / `subject_id` / `created_at` |

**幂等三处**：
- 重复 `start` 同一 `session_id` ⇒ 回报 `duplicate:true`，不新开一行。
- 重复 `end` ⇒ 首次的 `ended_at` / `end_reason` 不被覆盖（首次结束时间才是事实）。
- 重复事件 ⇒ 唯一索引 `(visitor_id, event, IFNULL(subject_id,-1), IFNULL(session_id,''))`
  挡住，回报 `duplicate:true`。
  语义：**同一访客、同一会话、同一题、同一事件只计一次**（前端重试不虚增）。
  表达式索引写法照 `verdictsStore.js:78` 的 `COALESCE` 先例。

## 4. 三个事件与「有没有人用过第二次」

- 事件枚举（写死，防脏事件名静默落空）：
  `question_created`（首次建题）/ `question_settled`（落定）/ `question_revisited`（回访）。
- ★**「有没有人第二次用过」= 同一访客名下的会话数 ≥ 2**，
  即 `summary.totals.returning_visitors` / `by_actor.{author,visitor}.returning_visitors`。
  这正是评审里「结构上没有答案」的那个数。
- **作者桶与非作者桶必须分开给**：混在一起的 PMF 数没有意义（作者天天用）。

### n<30 纪律

任何**比例**的分母 < 30 一律给 `null` + 一句人话 `note`（`rateBlock`）；
**原始计数照给**——它是事实，不是推断。
与 `auditKpi.brierCi`（`p1b/src/routes/auditKpi.js:81`）、
披露件 compiler 门面（`p1b/src/routes/disclosure.js:285`）同一口径。

## 5. 怎么查（两个入口）

**A. 端点（server.js 接上之后）**

```bash
curl http://localhost:8787/api/analytics/summary
```

**B. 不依赖 HTTP 的本地查询（此刻就能用，因为 server.js 未接）**

```bash
cd p1b && node -e "const {db}=require('./src/deps');db.init(db.DEFAULT_DB_PATH);const st=require('./src/db/analyticsStore');st.ensureAnalyticsTables(db.getConnection());console.log(JSON.stringify(st.summary(),null,2));db.closeCurrent()"
```

> 这一步会建出三张**空的** analytics 表（additive · 幂等 · 零行 · 不碰任何既有表）——
> 与启动服务时 `routes/analytics.js` 的 `register()` 做的是同一件事。
> 不先建表直接 `summary()` 会报 `no such table`（实测）。

验证输出（2026-09-28 跑在真实库上）：`author_key_configured:false`、
`totals.visitors:0`、`warnings` 里明写「服务端未配 P1B_AUTHOR_KEY ⇒ 谁也判不出作者」。

**C. 作者模式**：先起进程时带上 `P1B_AUTHOR_KEY=<你的密钥>`（Windows：
`set P1B_AUTHOR_KEY=... && node src/server.js`），再在浏览器
`localStorage.setItem('p1b_author_key','<同一个值>')`。之后 summary 里
`by_actor.author` 才是你自己的使用，`by_actor.visitor` 才是外部访客。
