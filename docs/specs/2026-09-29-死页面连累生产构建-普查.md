# 死页面连累生产构建 · 普查结果（2026-09-29）

> 起因：当天修过一个**真实的用户可见缺陷** —— `styles/charts.css` 只被 `ChartFrame.tsx` 引入，
> 而 `ChartFrame` 唯一的使用者是 8 个「死页面」之一（路由被 `<Navigate>` 重定向）
> ⇒ Vite tree-shaking 判定不可达，**整份样式表被摇出生产产物**
> ⇒ 活页上的 eyebrow 小标签（`.chart-eyebrow`）在生产环境**字号/字距/颜色全丢**。
> 产物复查：`.chart-eyebrow` / `.chart-legend` / `.chart-swatch` 全部 **0 → 1**。
>
> 那不是孤例。**本文件是普查结果。**

## 怎么查的

`p1b/web/src/dead-page-reachability.audit.mjs`（只读）：
以 **`main.tsx` ＋ 11 个活页组件** 为根做可达性遍历，列出走不到的模块。

死路径的定义：**路由的 `element` 是 `<Navigate …>`** ⇒ 组件根本不渲染，源码只留作禁词扫描的扫描目标。

## 结论一：那 8 个死页面在拖 26 个模块下水

```
死路径：/overview  /audit  /intake  /calendar  /compiler  /calibration
       /bayes-lens  /arena  /games  /input  /advisor  *
活页：  HomePage LivePage ManagePage SettingsPage MysticPage ResolvePage
       WhereOffPage NotePage NegativeResultsPage QuestionPage BaselinePage
```

## 结论二：但**只有 CSS 那一个是真实缺陷**

必须分清两件事，否则会把 26 个都当成 bug：

- **`styles/charts.css`** —— `components/ui/index.tsx:54` 用它的类，而 `components/ui` 被 **`App.tsx:31`** 与 **`QuestionPage.tsx:41`**（活页）引用 ⇒ **活页真缺样式**。已修。
- **`charts/*.tsx` 这些 React 组件** —— 它们的名字是 `.chart-eyebrow` 这类**类名**的唯一来源没错，但**组件本身**没有被任何活页用 ⇒ tree-shaking 摇掉它们是**正确行为**，活页无感。

判据已写进 `p1b/web/src/styles-reachability.test.mjs ①`：
**走不到 ＋ 类被活组件用 ⇒ 硬失败；走不到 ＋ 无人用 ⇒ 显形为提示。宁可漏报也不误报。**

## 结论三：ADR-005「删 8 个死页面」现在有具体数字了

那条建议原本写的是「删 2,524 行页面代码，把禁词扫描改扫 dist」。
普查把它量化成：**2,524 行页面 ＋ 26 个模块（含整个图表库 ＋ 3 个 lib）**。

★更关键的是**死页面现在有了一个已实证的失败模式**：
它不只是占代码 —— 它能**悄悄弄坏生产构建**（charts.css 已实证一次）。
所以「删掉它们」从「减负」变成了「消除一类静默故障源」。

**删之前要处理的三处依赖**（都不是拦路虎，但必须一起做）：
① `p1b/test/disclosure-phase4-pages.test.cjs` 与 `p1b/test/intake.test.cjs` 以源码路径引用它们（禁词扫描目标）
② `styles/tokens.test.mjs:53,116` 把 `intake.css` 等当设计令牌 lint 目标
③ `App.tsx:183-201` 那 11 条**重定向路由必须留着**（旧书签会 404）—— 删的是组件源码，不是路由
