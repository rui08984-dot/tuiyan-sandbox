# 阶段 5 · 检索可行性勘察（2026-09-15 · **v2 更正版**）

> ⚠ **本件更正 v1 的一处错误结论**。v1（本文件同路径的前一版）据「node `fetch` 直连全失败」判定
> 「路线 (a) 不可执行」——**该判定错误**：根因是**本机 `node fetch` 默认不走系统代理**，而本机 IE/系统代理
> 为 `127.0.0.1:2080`；加 `NODE_USE_ENV_PROXY=1` ＋ `HTTPS_PROXY=http://127.0.0.1:2080` 后，
> Wikipedia／GDELT／Bing／r.jina.ai／OpenAlex 等**均可达**（实测见 §一）。**路线 (a) 可执行**。
> v1 的错因如实留痕：我只测了「直连」未测「系统代理」，属**取数口径不完整**（与项目既往「只按一种口径取样即下结论」同类教训）。

> 用途：立项书 v1.1 §五-前置 2「信号源勘察交付件」的**检索侧**实测（resolve 侧见 `阶段5-功能映射表与信号源勘察-20260915.md` §三）。
> 本件另含 **§三 一项真值锚缺陷发现**（既有账本问题，非本立项引入）。

## 一 · 网络实测（2026-09-15 · 经系统代理）

### 1.1 代理事实（关键环境知识）

| 项 | 值 |
|---|---|
| 系统 IE/代理 | `127.0.0.1:2080`（注册表 `ProxyEnable=1, ProxyServer=127.0.0.1:2080`） |
| WinHTTP 代理 | **直连**（`netsh winhttp show proxy` ＝「直接访问」）⇒ **两条链路口径不同** |
| node `fetch` 默认 | **不走** 系统代理 ⇒ 对墙外源一律 `fetch failed`（这是 v1 误判的根因） |
| **可用姿势** | `NODE_USE_ENV_PROXY=1 HTTPS_PROXY=http://127.0.0.1:2080 node …`（实测 HTTP 200） |
| 替代姿势 | `http.request({method:'CONNECT',path:host+':443'})` 手工建隧道（本会话验证可用；**零依赖**） |

### 1.2 经代理可达性实测（HTTP 状态）

| 源 | 状态 | 时点合规能力 |
|---|---|---|
| **`en.wikipedia.org` `/w/api.php`** | **200** | ✅ `prop=revisions&rvprop=timestamp` ⇒ **可查页面历史版本**（判「cutoff 时点该页内容」的硬证据） |

## 二 · 检索策略（写死 · 拟入 PREREG 冻结件）

| 项 | 值 |
|---|---|
| **provider** | 直连（经系统代理），无第三方搜索 SaaS |
| **主检索源（按优先级）** | ① `en.wikipedia.org/w/api.php`（`action=query&list=search`，取条目；再 `prop=revisions` 取 cutoff 前最后版本）② `api.gdeltproject.org/api/v2/doc/doc`（`mode=artlist` ＋ **原生 `startdatetime/enddatetime`＝[cutoff−180d, cutoff]**）③ `www.bing.com/search`（补漏，无日期过滤 ⇒ 仅取 `r.jina.ai` 抽正文后**逐条做时点审计**） |
| **正文抽取** | `r.jina.ai/<url>`（返回纯文本＋`Published Time`）；失败 ⇒ 该条作废（不静默） |
| **query 模板** | `{{城市或主体}} {{指标中文名}} {{事件年月}}`（如「上海 最高气温 2026年9月」）＋ 英文等价式（维基/GDELT 英文库更全） |
| **日期过滤（写死）** | 只接受 `published_at < cutoff ∧ event_at < cutoff`；时点不明 ⇒ **丢弃**（不猜） |
| **条数** | 每题 **≤8 条**（≤3 源 × ≤3 条）；正文每段 ≤2000 字符入 prompt |
| **限速** | GDELT **≥5s/次**；其余 ≥1s/次；单题总预算 ≤20s |
| **禁** | **禁**访问 `resolve.url_template` 的主机/字段（防「抓真值锚冒充找证据」）；禁跳过时点审计直接喂 LLM |
| **原始快照** | 每条留 `url ＋ fetched_at ＋ 正文 hash ＋（若可得）Wikipedia revid / Wayback id` |

## 三 · ★ 真值锚缺陷发现（**既有账本问题**，非本立项引入）

### 3.1 现象（98 行 · 全部 realtime）

`openmeteo_forecast_daily_max` 98 行的 `resolve_note` 形如
`Open-Meteo forecast 2026-09-17 max=30.2C（阈值 >27，机检）`；**`resolved_at` 全部早于事件日**

⇒ 即：**结算时事件尚未发生，账本取的「真值」是当时的预报值，不是实际观测**。

### 3.2 量化（用 archive 实际观测复核，2026-09-15 实跑）

| 项 | 数 |
|---|---|
| 该 kind 总行 | 98 |
| archive **已有**实际观测 | 28（事件日 ≤ 今日） |
| ├ 与账本 outcome **一致** | 25 |
| └ **翻转**（应为另一值） | **3**（id=639/640/695） |
| archive 尚无观测（事件日在未来） | 70 |

⇒ **若把真值改为实际观测，账本 3 行 outcome 需翻转**（占已有观测行的 10.7%）。

### 3.3 定性（两层，须如实并列）

1. **真值口径**：resolve 用的是**预报**——事件日尚未到时，**不存在**「实际结果」；
2. **Q0-2 违例**：拒收门要求「cutoff 早于**事件决定性时点**」，而此 98 行的**结算**早于事件日 ⇒ 真值时点不成立。

### 3.4 对阶段 5 的直接影响

F2 池的 **realtime 子集 100% 就是这 98 行**。若原样入池：`retrieval` 臂检索到的「当时可得信息」与「作为真值的预报」**同源**（都是预报/天气资讯）⇒ **实验会变成「谁能复现当时的预报」**，而非「谁更接近事实」。**必须处置**（见 §五）。

## 四 · ★★ 决定性实证：证据产出率 = **0 / 52**（跨 25 个 kind）

### 4.1 实验设计

对池内**每个 kind 抽 2 题**（共 52 题 · 覆盖 25 kind），真跑「构造 query → Wikipedia 搜索 → 判定文本是否切题」。
**切题（真证据）的保守判据 = 三要素齐备**：主体词 ∧ 指标词 ∧ **事件日期**（缺一即 `no-evidence`）。

### 4.2 结果（`.tmp/evidence-yield.txt`）

| 项 | 数 |
|---|---|
| 抽样 | 52 |
| 主体词命中 | 10 |
| 指标词命中 | 19 |
| **日期命中** | **0** |
| **三要素齐备（真证据）** | **0** |
| ⇒ **证据产出率** | **0.0%** |

**返回的全是通用条目**（「Shanghai」「Exchange rate」「Air pollution」「Tide」「Electricity」），**没有一条**是对
「**某站某日**某指标**是否越过某阈值**」的可复核记叙。

### 4.3 GDELT 公平性验证（新闻源 · `.tmp/gdelt-fairness.txt`）

GDELT 是路线 (a) 的最强候选（新闻确实会报「BTC 暴涨」「上海高温」）：

- 「Bitcoin price」窗 2026-08-01..14 ⇒ **真正命中**（返回 5 篇行情报道）✅
- 「Shanghai heat wave」⇒ **429 限速**（实证 ≥5s/次 是硬约束，127 池分批将极慢）⚠
- 「Germany wind power」⇒ 429 ⚠

⇒ 即使对**极少数**「有新闻性」的题（加密行情、极端天气），GDELT 可用；但对池内**压倒多数**的
「城市日均 PM2.5 ≤ 6.4 μg/m³」「柏林日降水量 ≤ 0.9 mm」这类题，**新闻里根本不会逐日逐站报道**。

### 4.4 结构性根因（题面实测）

池内 **627 行**题面的形态：

| 特征 | 占比 |
|---|---|
| 含**精确阈值**（数值比较 `>= / <= / > / <`） | **100%** |
| 含**精确日期** `YYYY-MM-DD` | **100%** |
| 含具体观测站号/站点 | 7% |

⇒ 池是**「精确数值点预测」**题型（某主体、某日、某指标、越过某阈值），而**这类答案不在任何可检索文本源里**，
只在**结构化数值 API**（= `resolve` 自己的源）里。**检索式证据路线与本题池存在结构性错配**：
可检索的文本源提供的「同主体/同指标的一般知识」，与题目要的「该日该站的精确取值」**不是同一类信息**。

### 4.5 ★ 决定性论证：**路线 (a) 要么空、要么泄**（逻辑闭环，不依赖任何实测）

设某题的 **cutoff** 与 **事件日** e（立项书 §四-3 要求「页面发布时点 < cutoff ∧ 片段所述事件时点 < cutoff」）：

| 情形 | 结论 |
|---|---|
| **e 晚于 cutoff**（前瞻题：事件在判据冻结后才发生） | 任何「讲述该事件结果」的文本都必然发布于 **cutoff 之后** ⇒ **必被时点审计剔除** ⇒ 检索臂**拿不到任何切题证据（空）** |
| **e 早于 cutoff**（历史题：事件在冻结前已发生） | 讲该事件的文本**发布于 cutoff 前 ⇒ 合规通过** ⇒ 但那段文本**就是该题真值的来源内容** ⇒ **检索臂直接读出答案＝泄漏**（正是立项书 §四-3 明令禁的「抓真值锚冒充找证据」） |

⇒ **对「某主体某日某指标的精确取值 vs 阈值」这一题型，检索式证据在时点合规的前提下，不存在任何「既合规又切题」的信息**。
这不是数据源不够好，是**题型与方法的错配**（§4.4 已把成因实测到「池 100% 是精确数值点预测」）。

### 4.6 另两条独立阻碍（叠加）

1. **代理依赖**：本机 `node fetch` 默认不走系统代理 ⇒ 管线必须显式走 `127.0.0.1:2080`（**用户机器专属配置**，不可进冻结件）。
2. **限速**：GDELT **8 秒间隔实测仍 429**（`.tmp/gdelt-fair2.txt`：4 次要测中 3 次 429、1 次 fetch failed）；Wikipedia/其它 ≥1s/次。
   127 题 × 3 源 × (检索＋正文抽取＋审计) 的**检索预算远超立项书 §六 的估算**（§六 只算了 LLM 调用）。

## 八 · ★ 更新发现：**路线 (b) 前瞻数值信号 —— 有真增量且技术可行**

### 8.1 合法信号源

`previous-runs-api.open-meteo.com/v1/forecast?hourly=temperature_2m_previous_dayN`——
返回**提前 N 天实际发布**的预报存档（文档原文：「Data from past model runs is aligned to fixed lead-time offsets of 1–7 days. Requesting `temperature_2m_previous_day1` returns the value predicted **24 hours before valid time**」）⇒ **无未来函数**。

### 8.2 决定性实证（上海 × 10 日期 × 4 阈值 × lead 1/3 天）

| 臂 | Brier |
|---|---|
| **base**（历史基率，archive 常年同月频率） | **0.1523** |
| **signal**（previous_day1 预报存档，软概率） | **0.0771** |
| **signal**（previous_day3 预报存档，软概率） | **0.0833** |

| 提前量 | Δ | CI95（配对 bootstrap B=1000 seed=987654321） |
|---|---|---|
| **lead=1d** | **Δ=0.0752** | **[0.0319, 0.1216]** ⇒ **达标**（Δ≥0.02 ∧ 下界>0） |
| **lead=3d** | **Δ=0.0690** | **[0.0352, 0.1041]** ⇒ **达标** |

### 8.3 与原路线 (a) 的对照

| | 路线 (a) 检索式 | 路线 (b) 前瞻数值 |
|---|---|---|
| 证据来源 | 文本（新闻/百科） | **数值（气象模式存档）** |
| 是否泄漏 | **要么空要么泄** | **无泄漏**（`previous_dayN` = 当时实际发布的预报存档） |
| 增量 | **0/52 = 0%** | **Δ=0.072，CI 下界 >0** |

| 零 LLM 成本 | ❌ | ✅ |
| 覆盖域 | 全域（但实际 0） | 天气类 L3（**需重新建前瞻题**——事件日在未来） |

### 8.4 执行方案（阶段 5 重开 → 路线 (b)）

1. **新建前瞻题**（open-meteo forecast API 的 `models` 事件日 1–16 天后）→ 入账（走 Q0 拒收门）；
2. **在 cutoff 时点**抓 `previous_dayN` 预报存档（零 LLM 调用，纯 HTTP）；
3. **等事件日过后**用 archive 实况结算；
4. **对照**：`previous_dayN` 预报概率 vs 统计基率，配对 bootstrap（同 PREREG 口径）。

**工期**：建题 0.5 天 ｜ 等事件日 ≥3–16 天 ｜ 结算+报告 0.5 天。
**成本**：**零 LLM 调用**（纯数值）；需 open-meteo 免费 API（限速 600/日）。

### 8.5 局限（如实标注）

- 本实证 n=80（上海 × 10 日 × 4 阈 × 2 lead），**非预注册实验**——需正式 PREREG 后重跑；
- 覆盖**仅天气**（open-meteo 域），非全域；但「L3 短窗混沌」正是天气题的主要聚集层；
