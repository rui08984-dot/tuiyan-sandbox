### F1 ｜ 六层分类缺 L0 定义；L4 判据与「叠加层」语义自相矛盾 ｜ 严重度：中（框架级，可低成本修）
**证据路径**：docs/specs/2026-09-11-万物可预测性审计器-design.md:15-22（§1.2 判定顺序 L5→L6→L1→L3→L2→L4，末句「任何一层命中后停止（取最特殊层）」）；同文:65-70（§1.8 L4 第 3 问「是否无法用 L1-L3/L5 清单归层」；同节又称「L4 可以与 L2/L6 叠加，primary=底层，secondary=L4」）；docs/specs/万物分类清单-v2.md:11、42-45（同一矛盾原文）；docs/specs/2026-09-11-万物可预测性审计器-design.md:141（审计器自称「L0-L3 阶梯的旁路试点」）；.scratch/forecast-debate/D-裁决.md:37（L0=预测卡「n≥30 局∧200 条前只记不评」门禁）。
**具体问题**：①**六层文档里没有 L0 定义**——L0 实为「L0-L5 演化阶梯」的记账级门禁（C-创新.md:41），与「L1-L6 可预测性分层」是两套同名编号，跨文档引用必生歧义。②按判定顺序，任何可归 L2/L6 的题都在 L4 之前命中并停止 → L4 第 3 问永远为假；而 L4 又要求「叠加在 L2/L6 上」——两条不可能同时成立。③实测尚未爆：全库 secondary_layer 非空 = 0 行（SQL：SELECT COUNT(*) FROM predictions WHERE secondary_layer IS NOT NULL → 0），即 L4 从未触发。
**建议修法**：清单 v3 把六层改名去数字（DET/ENS/CHA/REF/RND/ADV），或显式声明「本清单 L1-L6 与 C 棒 L0-L5 阶梯是两套编号」；L4 第 3 问删去互斥条款，改为「在底层判定**之后**追加 REF 标记（primary=底层，secondary=REF）」，并把 L4 从决策树尾节点改为后置标注步骤。

### F2 ｜ 可判定率分子含未来状态 + 分母含永久无法判定的题 ⇒ G2 一票否决门在正常运营下结构性卡死 ｜ 严重度：**高**
**证据路径**：docs/specs/2026-09-11-万物可预测性审计器-design.md:114（分子定义「resolved+voided 题中…」÷「提交总题数」）；p1b/scripts/g2-report.cjs:30-31、38-46（实现：RESOLVED 要求 outcome 非空 ∧ resolved_at 非空；judgeable=resolved ∧ checklist_hash 非空 ∧ 锚可机检；rate=judgeable/total）。
**复现**：node p1b/scripts/g2-report.cjs → 「可判定率 = 602 / 1040 = 57.9% → 未达标」，分窗 realtime 450 / backfill 152。（同一分母随新题入库持续下移：审查后段重跑 SQL 得 602/1503 = 40.1%，判据冻结率上限仅 624/1503 = 41.5%——**该门在现有生产形态下上限即 <70%，不可能达标**。）
**具体问题**：①G2 表把可判定率定义为「resolved+voided 题中…÷提交总题数」，但**可判定性（判据冻结+锚存在）在提交时即已确定**，与将来能否 resolve 无关；实现的分子只数已 resolve 的行 → 该指标实为「已结算占比」，被在途题（实测 438 条未解，其中 corpus forward 多为 2026-10/11 到期）机械稀释。②本库另有 450 条已 resolve 却无 resolve 参数的行（SQL：evidence_json 无 resolve 键 → 450/450 且全部已 resolved），它们永远无法以 resolved+voided 形态回来，永久压在分母上。③后果：判定者**现在**就可按字面判定 G2 失败（57.9% < 70%），与「G2 最快 11 月底」的叙事矛盾——门禁可能已在无意中被判死，而路线图把它当作未来才到期的时间门（docs/specs/推演沙盘-终极路线图-20260913.md:56）。
**建议修法**：可判定率改为**提交时判定**：分母=已提交题数（或已到期题数），分子=checklist_hash 非空 ∧ 锚可机检（不要求已 resolve）；在途题单列 pending_resolved；backfill 按 R3 独立读数。
### F3 ｜ G2 三指标可被「新题洪流」稀释——比 R3 已修的 backfill 灌水更严重的 Goodhart 漏洞 ｜ 严重度：**高**
**证据路径**：docs/specs/2026-09-11-万物可预测性审计器-design.md:114（可判定率分母=提交总题数）；p1b/scripts/g2-report.cjs:36-46（total=全库 COUNT）；docs/specs/语料库历史回填-加速计划-20260912.md:29、96（「今天就能把 L2/L3/L5 从 22 条做到 100+ 条」→ 实测已到 1503 行）；docs/specs/推演沙盘-终极路线图-20260913.md:22-24、52（语料扩展=阶段 2 主线，非对局题 22→286→590）。
**具体问题**：R3 只堵了「backfill 冒充吞吐」，没堵「用未来题稀释比例」。可判定率与争议率的分母是**提交总题数**（含 438 条在途），于是「多铺未来题」这一被路线图定为**主线**的动作，会直接压低可判定率读数——题越多门越难过，与「多找数据源、加速铺量」的用户指令方向相反。实测：单次审查期间分母 1040→1503（+463 条），可判定率 57.9%→40.1%，而这不是能力下降，纯粹是分母增长。
**建议修法**：三指标一律改为**队列制（cohort）口径**：按「到期月」分桶（resolved_at 或 evidence 目标日），只对已到期题计算比率；未到期题单列 `pending`。R3 ④分窗条款同步扩为「分窗 × 分队列」二维。

### F4 ｜ 「技术强制防作弊」不成立：题与真值同表同库，真值可被参与方直接读出 ｜ 严重度：**高**（这是本报告最硬的一条）
**证据路径**：p1b/scripts/corpus-backfill.cjs:290-303（backfill 题把 `truth_preview`（历史实测真值）与 `resolve` 参数一起写进 evidence_json 落库，checklistHash='bf1'）；SQL：SELECT COUNT(*) FROM predictions WHERE evidence_json LIKE '%truth_preview%' → **152**；实例：id=473 evidence[0].truth_preview=7.7 而同一行 outcome=false（0/1 与真值同表可读）；forward 批同样把 `resolve`（含 url_template/日期/阈值）写进 evidence_json（id=1497 例），而 p1b/src/routes/verdicts.js:100-148 的 loadEvidence **正是从同一张表的 evidence_json 取证据入 prompt**。
**具体问题**：用户要求「防作弊必须技术强制（脚本物理上拿不到 cutoff 后数据）」（docs/specs/讨论汇总与实施路线-20260913.md:50），但当前设计的「技术强制」只约束了**取数脚本**（corpus-resolve-daemon.cjs:147-156 的到期守卫、daemon 只跑到期题），没有约束**库内可见性**：凡能读 p1a.db 的进程（含将来的回测引擎、判词路、任何 agent）都能一次 SELECT 拿到真值。对 L2/L3/L5 的机械引擎这尚可容忍（它们本就只算基率），但一旦把「判词/LLM 路」接进同库（路线图阶段 4 明说 L6 用判词修复成果），回测分数即被污染——而 D2 明确计划用回测分数当能力证据。
**建议修法**：物理分库分表：`predictions`（题面+判据+cutoff）与 `truth_vault`（真值+resolve 参数）分离，truth_vault 只允许 resolver 进程读；backfill 批补一次迁移把 truth_preview 从 evidence_json 剥离；回测引擎以**只读题面视图**运行，且以「能否 SELECT 到真值」作为防作弊复测判据。
### F5 ｜ 「月 resolve 吞吐」与 D1 修订版都不测能力——G2 里没有一条指标在测「预测质量」 ｜ 严重度：中-高
**证据路径**：docs/specs/2026-09-11-万物可预测性审计器-design.md:110（终审口径：三过程指标达标才放行，Brier 仅描述性）；同文:116（吞吐「≥30/月，连续 2 个月」，理由「n≥30 对齐 F13 准入」）；.scratch/forecast-debate/全文精读/K-公式精读.md:101-102（**F13 原文=conformal 校准集覆盖 ±0.05 需 n≈102，ε=0.1 需 22；F13 是「校准集大小需求表」，与「月 resolve 吞吐」无任何推导关系**）；docs/specs/讨论汇总与实施路线-20260913.md:64-69（D1 建议：累计 ≥60 + 覆盖 ≥2 个不同月份 + 难度分层报告）。
**具体问题**：①**F13 引用是误引**：F13 讲的是「要估准覆盖率需要多少校准样本」，不能推出「每月 30 条已 resolve」这个运营读数；真正与 F13 同源的应是 L0 门禁的 n≥102/200。②把「连续 2 月」换成「累计 ≥60 + 覆盖 ≥2 月」在统计上确实更合理（原口径的「防单月偶然」不成立——1000 条一月与分散三月证据强度相同），用户 U4 的质疑成立；**但修订后仍只测「还在产出」，不测「产出得准不准」**。③后果：一个把所有题都写成 0.5、或只收「抛硬币级」简单题的系统，可以完美通过 G2（可判定率 100% + 争议率 0 + 吞吐达标），然后解锁 L3 检索代码与「分层预测平台」升级（docs/specs/推演沙盘-终极路线图-20260913.md:27-30）——这与项目自己写下的「防 Goodhart」初衷（同文:28「防 Goodhart 条款已内建」）直接冲突。
**建议修法**：G2 增列一条**最低质量门**（不必是 Brier 绝对值，可为「分层基线对照」）：至少一个层（如 L2）在 n≥60 且 ≥2 个自然月的样本上，Brier 严格优于该层常数基率 b(1−b) 下限，且分辨率分量 >0（Murphy 分解，防「全员 0.5 假校准」——C-创新.md:44 L3 已写好这条判据，只是没进 G2）。若担心门槛过高，可把该条设为「解锁 L3 检索」的必要条件，而把过程指标保留为「维持平台运行」的充分条件。

### F6 ｜ G4 在盘上无定义——D1 表把「G4」当保留项，但 G4 只在终审表出现一次 ｜ 严重度：低
**证据路径**：docs/specs/讨论汇总与实施路线-20260913.md:67（「运营门 G4（4 周无活动→冻结）」）；docs/sandbox/upgrade-review-20260909/00-终审方案.md:44（**G4 唯一出处**：「4 周无新局/无 resolve → 只维护不开发」）。
**具体问题**：D1 把 G4 当作既有运营门引用，但它在审计器 design §4 里完全没有登记，也没有任何脚本/视图实现（全库 grep：p1b/scripts 无 G4 相关代码）。G4 的定义是「无新局/无 resolve」，而当前语料线的 resolve 由 daemon 自动跑——**daemon 空转一天也会让 G4 永不触发**，与设计意图（测「人还在不在」）不符。
**建议修法**：把 G4 登记进审计器 design §4 并实现为月报一行（区分 realtime/backfill 两个活动计数）；或明确它已被「daemon 自动 resolve + 语料线」取代而删除。
### F7 ｜ 「难度=基率偏离 0.5」把**信息量**当成了难度，且与同批报告的另一处口径打架（62.1% vs 65.9%） ｜ 严重度：中
**证据路径**：docs/specs/讨论汇总与实施路线-20260913.md:80-86（D3 表：hard 646 / mid 307 / near 83 / extreme 4；分层难题占比 L3 83.7% / L5 41.7%）；实测复算脚本回执 p1b/sim/out/_diff.txt（「=== 难度分布（基率偏离 0.5 程度）===」「平均偏离 0.5: 0.1250 | 样本 1040」「各层平均偏离 + 难题占比（偏离<=0.15 算难题）」）。
**具体问题**：①**定义与数字对不上**：D3 表头写「hard (基率 0.35-0.65)」，按区间定义复算得 685 条（65.9%）；而 646 条（62.1%）来自**偏离定义 |p−0.5| ≤ 0.15**（SQL 复算：p=0.35 的 22 条与 p=0.65 的 17 条恰好落在两个定义的分界，共 39 条差异）。同一张表里的数字与标签不是同一套算法。②**度量选错**：`assigned_prob` 是**我们自己填的概率**，偏离 0.5 度量的是「我们敢不敢给极端值」，不是「题目难不难」。极端题（正确答案 0.02）如果被我们诚实标 0.02，会因「偏离大」被记为 near/extreme（**容易**）；而被标 0.5 的题反而记为 hard。用同一个概率既当预测值又当难度标签，是**循环度量**。③实测反向证据：L3 层 83.7% 记为 hard，但 L3 的 p 由气候基率算出（mean |p−0.5| = 0.0665）——「难题占比最高」与「离 0.5 最近」是同一句话，等于说「我们的天气题都被标成接近 0.5」，与真实难度无关。④这直接支撑了用户 U5 的错误结论被**否证**的方式：D3 用「62% hard」反驳用户「都是简单题」，但该度量不能反驳也不能支持该命题。
**建议修法**：难度改用**外生**度量，三选一（可并行）：(a) **基率熵/基线 Brier 下限** b(1−b)（外生于我们的填值，PREREG-RB 已在用）；(b) **基线对照增量** ΔBrier = b(1−b) − 本引擎 Brier（「难」= 基线做不好）；(c) **horizon × 事件稀有度**分层（D3 已有 horizon 数据：短 131/中 67/长 111，见 p1b/sim/out/_hz.txt）。至少应在报表中把「难度」列改名为「填值极端度」，避免下游误读。

### F8 ｜ 「1040 条实测」的口径混淆：D4 的体检表把不同批次的指标并列 ｜ 严重度：低-中
**证据路径**：docs/specs/讨论汇总与实施路线-20260913.md:91-97（D4 表：无 evidence 的题 0；无 resolve 参数 0/438；gate 全 descriptive 1040/1040；六层分布）；p1b/sim/out/_audit.txt（同批回执）；实测复算：evidence_json 中「无 resolve 键」的行 = **450 条**（全部已 resolve，即 v1/v2 的 R-A/R-B 判据批次），另有 152 条 backfill 含 truth_preview；六层分布 L6 26%/L3 23.7%/L2 22.7%/L1 17.3%/L5 10.4% 对应的分母是**全部 1040**（含 450 条无 resolve 参数的对局题），而 G2 报告用的是另一套分母。
**具体问题**：D4 的「无 resolve 参数 0/438」只覆盖未解题，读者会误以为全库题都带 resolve 参数；实际上 450 条已解对局题**没有任何 resolve 参数**（它们的真值来自程序结算），这正是 F2 里「永久压在分母上」的那批。同一份 D4 表混用了「全库 / 未解 / 已解」三种分母，而 G2 报告另用一套——三处数字都对，但并列会让读者得出错误整体判断。
**建议修法**：D4 每行标注分母（全库 N=1040 / 未解 N=438 / 已解 N=602），并对「无 resolve 参数」按已解/未解分别计数（当前实测 450/0）。

### F14 ｜ 库内两批数据形态互斥，导致任何「全库校准结论」都不可用 ｜ 严重度：中
**证据路径**：实测 SQL（只读）：`SELECT checklist_hash, COUNT(*), SUM(outcome IS NOT NULL) FROM predictions GROUP BY checklist_hash` → NULL 879/0 解、bf1 152/152 解、v1 90/90 解、v2 382/360 解。另：`SELECT COUNT(*) FROM predictions WHERE created_at = resolved_at` → 450（即 v1+v2 的 R-A/R-B 批为**瞬时 resolve**：resolve 时间戳与创建时间戳逐秒相同，median 延迟 0 秒、最大 80 秒）。
