# 基座对外交付方案：让别的 AI 装上它之后能干什么

> **日期**：2026-09-30 · **基线**：`d0703c6` 之后 · **一次转向的产物**
> **一句话**：前 23 天做成了一个「判断记账基座」，但最近四轮全在做图形界面。
> **本方案把主线换回来**：**基座的价值在接口层，不在页面**。

---

## 〇、这次转向是怎么来的

创始人的判断（原话要点）：「做的只有基座，但是后台这一块叫 MCP……其实没有必要去做成那种图形界面」
「主要是要确保我们整个的项目的框架所有的代码还有所有的功能都可以被调用」
「每一个功能都可以互相融洽、互相耦合、互相联动的使用，那是更好的」

**我认这个判断，并且要认自己的账**：最近四批（`0e5db61` / `3340b62` / `0982be1` / `32b426c` / `13a4a78`）
做的全是「页面 ＋ 打包 ＋ 好不好看」，**没有一批在做接口与开源分发**。

原因是我照着《产品化交付方案》做的，那份方案通篇在讲「陌生人双击就能用」。
**那对「做一个好用的软件」是正确的判断，放到「做一个基座」身上就是跑偏。**

**「双击即用」做完一次就够了，不值得连做四轮。**

## 一、这套系统到底是什么（比喻版）

**它是一个「公证处」。**

- 法院告诉你**谁有道理**（那是律师和法官的事）
- 公证处只做一件事：**如实记录，且记录之后不许改**，再给你一张「这份记录没被动过」的证明

它**不预测**（那是专家的事），**不建议你**（那是理财顾问的事）。
它只做一件别人不做的事：**记下你的判断，然后证明你没事后改口。**

围绕这个公证处搭了三层：

```
【底座】六层分类 ＋ 六个算子 ＋ 53 个取数源 ＋ 只写不改的账本
   ↓
【接口】23 条命令行 ＋ MCP 接口 ＋ HTTP     ← ★本方案的主战场
   ↓
【皮】  五个网页页面 ＋ 绿色 zip              ← 已够用，不急
```

★**对一个基座来说，「皮」做得再好，别人也接不进来**——他没法让你的网页给他算分。

## 二、★本方案的核心交付物：「别的 AI 装上它能干什么」

**这是唯一真正要新写的东西。** 不是代码，是一份**能力目录**，
形状是「用户这么说 → 它调这个 → 得到什么」。

### 2.1 为什么这是最要紧的一件事

一个基座对外交付时，别人第一个问题是「**这东西对我有什么用**」。
而现在：

- 23 条 CLI 命令**能用但没人知道**
- MCP 接口 18 个工具**写好了但没发布**
- 11 条负结果**有页面但没入口**
- 六层分类、六个算子、53 个取数源**在界面里全都不露**

⇒ 这不是「宣传不足」，是**接口的语义没有被写下来**。没有那份目录，
别人装上 MCP 之后面对 18 个工具名，仍然不知道该调哪个。

### 2.2 能力目录的形状（**这份表就是主交付物**）

每一条都必须写满五栏，缺一栏不算完成：

| 栏 | 内容 |
|---|---|
| **用户这么说** | 一句**自然语言**，不是工具名（❌「调用 `ledger_score`」／✅「我这半年关于汇率的判断准吗」） |
| **它调什么** | 具体的 MCP 工具名 ＋ 该工具背后的六层/算子/取数源 |
| **得到什么** | 返回的**结构**（字段级），不是「一些结果」 |
| **不能做什么** | ★**这一栏不许空**。它不预测、不给建议、不碰私钥——把边界写在工具旁边，而不是让调用方踩了才知道 |
| **越界了怎么办** | 该工具对**不满足前提**的输入返回什么（fail-closed 的具体口径） |

★**第四栏和第五栏是这个项目的独有之处**。市面上同类工具没有，
因为它们不设边界、也不对边界负责。

### 2.3 要覆盖的四类能力（按「用户会问什么」归组，不按代码目录归组）

| 组 | 用户会怎么问 | 背后用到 |
|---|---|---|
| **打分** | 「我的判断准吗」「在同类事上我偏不偏」 | 六层分类 ＋ `l2_baseline` 算子 ＋ 账本 |
| **记账** | 「记一道」「这道题到期了吗」「这批题是谁的」 | 账本（只写不改）＋ 归属三桶 |
| **审计** | 「这批数据被改过吗」「有没有真值混进判断题」 | 冻结哈希 ＋ 泄漏扫描 ＋ CLI |
| **裁决** | 「这事能不能自动结」「该给它归哪一层」 | 六层分类 ＋ 53 个取数源 ＋ reveal-class |

★**这四组之间必须能联动**，这是创始人明确要的。例如：
「记一道题」→「自动归层」→「到期自动结」→「算进我的准确率」→「指出我在哪类事上偏」
应该能**一串跑完**，而不是调用方自己拼五个工具。

### 2.4 ★「所有功能都能被调用」——覆盖率审计（先数，再补）

**不能假定「写了就等于能调」。** 本方案要求做一张**覆盖率对账表**：

```
codebase 里有几件事  ──vs──  MCP 暴露了几件事
```

对不上的每一项，三选一，且必须写进表：
- ① 补上 MCP 工具（若它对外部有用）
- ② **明确标注「不对外」并给理由**（若它是内部实现，例：某条命令的自测缝）
- ③ 合并进已有工具（若它是同一件事的另一半）

★**判据：任何一件 codebase 里能跑的事，表里必须有一行结论。**
「没提到」不算结论，「忘了」是最大的漏洞。

## 三、★联动：把「一串跑完」变成可承诺的东西

创始人要的是「互相耦合、互相联动」。落地成三条**可测试**的承诺：

| # | 承诺 | 怎么验 |
|---|---|---|
| **L1** | 调用方只需说一句话，**不需要知道内部有几个工具** | 一个「意图 → 工具序列」的映射表，每条都跑通 |
| **L2** | **一条链跑完，中间任何一步不满足前提就停下并说清哪一步** | 对每条链做**中途投毒**测试：破坏第 k 步的前提 ⇒ 必须停在那一步，且**前 k-1 步的写入被如实报告**（不回滚，但要留痕） |
| **L3** | 六层分类与取数源的判定**对调用方可见**，不是黑盒 | 返回体里带**为什么这么归类**的理由字段（`revealClass.js` 已有 `why`，须一路透传到 MCP 层） |

★**L2 的「不回滚但留痕」是有意的**：账本不可变是硬边界，
所以半途失败时**不能假装没发生过**，只能如实说「前 3 步已写入、第 4 步没成」。

## 四、分发形态：MCP 为主，其余顺带

| 形态 | 给谁 | 本方案的动作 |
|---|---|---|
| **MCP** | ★**主要形态**：所有 AI 工具 | 填正经名字 ＋ 能力目录 ＋ 发布说明 ＋ **联动链** |
| **CLI** | 人、脚本、CI | 已有 23 条，**补一份与能力目录对照的索引**即可 |
| **HTTP** | 任何能发请求的东西 | 已在跑，**补对外文档**（现在是零文档） |
| **npm** | 开发者 | P1，取决于 MCP 走通的先后 |
| **绿色 zip** | 不会用 Node 的人 | **已完成，不再投入** |

★**先做 MCP 的理由**：它是唯一一种「装上就有用」的形态——
别人不用理解你的世界观，只要装上、说一句「帮我审计一下这批预测」，就有用了。
其余形态都是「要他先理解你」的形态，成本高、转化低。

### 4.1 发布时 GitHub 上必须有的三份文件

| 文件 | 回答什么问题 | 现在有没有 |
|---|---|---|
| **能力目录** | 「它能干什么」「用户这么说它会调什么」 | ❌ **本方案新建** |
| **安装说明** | 「怎么装」「装完怎么验证装对了」 | ❌ 新建 |
| **README** | 「这是什么、为什么值得信」 | ⚠️ 有（71 行，偏开发者）⇒ **补一节能力目录的摘要** |

★**不要写成宣传文案**。要写成**可以被机器验证的说明书**：
每条能力都要有一个「调用示例」，示例能跑通才算写完。

| 批 | 做什么 | 完成判据 |
|---|---|---|
| **A** | **覆盖率对账**：codebase 有几件事 vs MCP 暴露几件事，逐项给结论 | 表里**每一项都有结论**（补上／不对外＋理由／合并） |

### ★⚠️ 对账已经能看出的三件事（不用等人工逐项过）

**① MCP 工具名是写给机器看的，一句话都读不懂。**
18 个全是 `p1b_doctor_board` / `p1b_read_g2_report` / `p1b_audit_prereg_freeze` 这种形态。
装上它的人不会知道该调哪个——**这就是能力目录必须存在的原因**，
而且比原方案估计的更急：不是「文档没写」，是**名字本身不表意**。

**② MCP 暴露的 18 个里，「读」占 5 个、「审计」占 4 个、「体检」占 5 个、「备份」占 2 个、「结算」占 1 个、
「读数/分层」等另若干 —— 覆盖的是「审计与体检」这一侧。**

★**缺口很清楚**：
- **「记一道题」没有 MCP 工具** ⇒ 别的 AI **不能替你写预测**（`p1b_settle_corpus` 是结算语料库，不是「把我的判断记进账本」）
- **「算我的准确率／我在哪类事上偏」没有 MCP 工具** ⇒ 别的 AI 拿不到打分，只能看审计结果
- 「六层归类」没有独立工具

⇒ 这三条正好落在方案 §2.3 的**「打分」「记账」「裁决」三组**里，是第一批要补的。

**③ CLI 23 条 vs MCP 18 个，覆盖率不是「都覆盖了」。**
23 − 18 = 5 条差集，但更重要的是**方向相反**：CLI 里有「读数 / 分层 / 欠账 / 抽检清单」这类
**直接回答「我准不准」的**命令，而 MCP 那 18 个偏审计体检。
⇒ **MCP 缺的恰好是最对外的那几件**。
