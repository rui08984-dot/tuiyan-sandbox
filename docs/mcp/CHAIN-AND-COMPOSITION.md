## 0. 先纠正这一版的前提

上一版把四组能力串成**链**。这一版改成图，并且实跑之后发现：**示例里那条直线
在代码里不是四个节点，是三个。**

| 上一版写的直线 | 代码里实际是什么 |
|---|---|
| 归类 → 取值 → **拒收门** → 记账 | `拒收门` 是 `归类` **内部的一个分支**，不是独立一步 |

依据：`p1b/src/routes/intake.js:296` 的 `classifyIntake` 一个函数里按顺序做
① 实验场域门（`:309`）② 拒收门三问（`:329`）③ 决策树定层（`:350`）④ 引擎（`:386`）。
所以**拒收门跑在定层之前**，不是「取值之后再来一道门」。

⇒ 本件的直线形态按**代码实际形状**记作 `S1 归层（含拒收门） → S2 取值 → S3 记账`，
三步。投毒表里我把「破坏拒收门」标成 **S1 内部分支**，不假装它是第 3 步。

**另一处纠正**：回溯的扳机（取不到真值）**不是停机理由**。我第一版把它当失败就停，
结果组合② 永远走不到回溯那一步。实跑逼出来的正确形状是三种返回：
`ok`（前进）／`trigger`（预期失败，走回溯边）／`stop`（停机）。

## 2. 组合契约

### 2.1 组合① 直线

```
S1 归层(含拒收门) → S2 取值 → S3 记账
```

| | 内容 |
|---|---|
| **前提** | ① 题面非空 + checklist 齐全（Q0_1/2/3 + L5/L6/L1/L3/L2 各层，L4 可选）；② `resolve_spec.kind` 在支持表内；③ 同类已结算题 n ≥ 30 |
| **产出** | ① 一行 `intake_questions`（或 `intake_rejects`）；② 一个 Wilson 区间 `interval:[lo,hi]` + 点估计；③ 一行 `predictions`（id + 容器局 id） |
| **失败停在哪** | 拒收门 → **停在 S1**；n<30 → **停在 S2**；prob 非数值/缺 kind → **停在 S3** |
| **实测** | 走通：S1 layer=L3 → S2 `state=enough, n=113` → S3 201 id=2010。写入清点 `{predictions:1, intake_questions:1}` |

### 2.2 组合② 回溯

```
S1 归层 → S2 记初判 → S3 取真值 ─(取不到 ⇒ 扳机)→ S4 揭晓分流 → S5 换层/换源重试 → 追加新题
```

| | 内容 |
|---|---|
| **前提** | 同①，另加：真值此刻**还拿不到**（未到期，或 kind 属 stuck） |
| **产出** | 旧题留在未落定清单（**不会被消除**）＋ 一条新题 |
| **失败停在哪** | S3 若**不是**「取不到」而是别的原因 → 停 S3；S5 换层非法 → 停 S5 |
| **实测** | 走通：S3 返 409 未到期 → 扳机 → S4 分流 `{ok:12, need_human:11, stuck:13, open_total:36}` → S5 换层 L2 + 追加 id=2012。账本 2 行、`resolved=0` |
| **★试几次** | 本件裁定 **≤2**。理由：换层换源各试一次仍取不到，说明是**真值源本身**的问题（`stuck`），再换层只是换一种错 |

**★回溯边为什么必须有次数上限**：`stuck` 类（`revealClass.js:68-69`：`cta_daily_total_rides` 地域封禁、
`oddsapi_h2h` 真值窗口已滑出）是**kind 的固有属性**，不是运行时抖动。换层不改变 kind ⇒ 永远取不到。
实测当天 stuck 桶 13 条 —— **占未落定 36 条的 36%**，不是小众路径。

### 2.3 组合③ 回环

```
S1 记一道 → S2 结算 → S3 打分 → S4 偏差检测 → ★回写一条**新**判断(追加) → 下一轮 S1
```

| | 内容 |
|---|---|
| **前提** | 同①；且**回写必须带 `Idempotency-Key`**（AI 客户端默认重试） |
| **产出** | 每轮**新增一行** `predictions`，旧行一列不改 |
| **失败停在哪** | prob 非数值 → 停 S1；未到期硬结算 → 停 S2；**本轮 n<30** → 停 S3（不许回写） |
| **实测** | 3 轮全走通，prob 0.85→0.55→0.40，每轮 Brier 0.7225→0.3025→0.1600，Δ=[−0.42, −0.1425] |

**★回环的核心纪律：每轮只能追加，不能改写。**
实测 ③ 三轮累计 `predictions=3`（不是 1 行被改 3 次），`resolved=3`。
第一轮那道题一旦结算，它的 `prob=0.85` 就永久留在账本里——**错的那次判断本身就是数据**。
这不是缺陷，这是「知道自己哪儿不行」得以被测量的前提。

**幂等（回环最典型的污染源）实测**：
| 调用 | 结果 |
|---|---|
| 同键同体，首次 | 201 id=2021 `idempotency-status: first-write` |
| 同键同体，重放 | 201 **id=2021**（同一个 id）`replayed`，账本不多写 |
| 同键**异体** | **409**，报两个请求指纹 |
| **不带键**的老调用方 | 201 id=2022 `absent`，**照写**（不静默改成拒绝） |

## 4. 收敛条件（★不许写「一直转」）

### 4.1 三条停机规则

| # | 条件 | 含义 |
|---|---|---|
| ① | **轮数 = 3** | 硬上限。到点必停 |
| ② | 本轮 Brier ≥ 上一轮 | 偏差不再缩小 ⇒ 继续转没有收益 |
| ③ | 某轮 Brier 样本 **n = 0** | 读不出来 ⇒ 无从判断收敛 |

三条**任一命中即停**。实测 RUN=COMPO0XOFQ：命中 ①，判定 `converged:true, reason:"达轮数上限 3"`。

### 4.2 ★但这三条里，只有一条真的会响

**实测：规则 ② 在 n=1 时永远不会触发。**

第 1 轮 Brier=0.7225、第 2 轮 0.3025、第 3 轮 0.1600，Δ 全是负——但这是
**单次伯努利试验的代数**（`(0.85−0)²=0.7225`、`(0.55−0)²=0.3025`、`(0.40−0)²=0.16`），
不是「校准变好了」的证据。真值我固定成了 `false`，prob 我手工一路往下调，
所以 Δ 必然单调下降。**换成别的序列它照样可以单调上升。**

⇒ **诚实写法**：规则 ② 的前提是「有一个 n≥30 的可信读数」。在 n=1 上，
**能真正生效的只有规则 ①（轮数上限）和规则 ③（n=0）**。
这不是规则的缺陷，是 n<30 纪律（`l2_baseline.js` 的 `MIN_N=30`）的直接后果：
**一条判断永远不足以判断自己。**

**推论（回环的真正节流阀）**：回环要转出有意义的轮次，靠的不是多转，
而是**攒够同一个域/层的已结算题到 n≥30**——那时规则 ② 才开始有牙齿。
在攒够之前，回环唯一诚实的动作是**只记方向、不出比例**（`habitRank.mjs:66` 的
`dropped` 口径同款）。

### 4.3 收敛判定的落点

```
delta = brier[round] - brier[round-1]
if round >= 3:                    → 停（达上限）
if delta >= 0:                    → 停（不再缩小）★需 n ≥ 30 才有意义
if brier_n == 0:                  → 停（读不出来）
else:                             → 下一轮，追加一条新判断
```

## 5. 实跑带出来的三个坑（不是形状问题，是跑起来才看见的）

### 坑① `GET /api/baseline/:kind` 的 `ok` **不表示「你拿到数了」**

`routes/baseline.js:142` 的 `buildReading` 对 `enough` / `too_thin` / `no_rows`
**三态一律返回 `ok: true`**。实测：`cwl_ssq_blue_odd_forward`（账本 0 条）返回
**HTTP 200 + `ok:true`**，只有 `enough:false` / `state:"no_rows"` 告诉你其实没有数。

⇒ **只判 `ok` 的 AI 调用方会在 n=0 时以为拿到了读数。** 真信号是 `enough` / `state`。
本件的所有取值步都按 `b.enough === true` 判成功，不是按 `ok`。

### 坑② 防泄漏闸有**同秒缺口**（★这条是跑出来的，不是读出来的）

`verdictsStore.js:175` 的 `leakState` 判据是 `String(now) <= resolvedAt` 就放行，
而 `resolved_at` 与 `now` **都是 `datetime('now')`，秒级精度**（`:434` 与 `:215`）。
⇒ 结算与判词生成**落在同一秒**时，闸判 `clean` 放行。

实测对照（同一轮跑、同一 kind）：

| 场景 | 结果 |
|---|---|
| 结算后**同秒**要判词 | **200，3 条判词照写进 verdicts** |
| 结算后**隔 2.5 秒**要判词 | **409**「这道题已结算…那是拿着答案回头看」 |

⇒ 这条闸在真实调用里挡得住「事后回看」，但**挡不住同一秒内的竞态**。
对回环尤其要紧：回环的第 2 步正是结算，紧接着就有人要判词。
**未修**（本轮只诊断，不动 `verdictsStore` 的判据——改它动的是读侧口径，须另立项）。

### 坑③ 「取不到真值」在链式思维里是**死路**，在图里才是**入口**

我第一版把「取不到真值」当失败就停 ⇒ 组合② 永远走不到回溯。
实跑逼出来的三种返回才是对的：`ok` / `trigger`（预期失败，走回溯边）/ `stop`（停机）。
**回溯边必须有「预期失败」这个第四种状态**，否则图退化成链。
