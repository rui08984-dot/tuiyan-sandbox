## 二、InkOS 可改性：基础事实

| 项 | 值 |
|---|---|
| 版本 / 许可 | **1.8.0 ／ AGPL-3.0-only** ⚠（自用无碍；一旦分发或对外提供服务，有开源义务） |
| 上游仓库 | `github.com/Narcooo/inkos`，monorepo（`packages/cli` · `packages/core` · `packages/studio`） |
| 包内代码 | **完全没有压缩/混淆**，标准 tsc 输出，完整 JSDoc、有意义变量名、**264 个 `.d.ts`** 齐全 |
| 规模 | CLI 7.4k 行 ＋ core **46.8k 行** ＋ studio API 10.5k 行 ≈ **65k 行 JS ＋ 16k 行 .d.ts** |
| 源码可取回？ | **不能从包内取**：有 `.js.map` 但 **`sourcesContent` 全部缺失**（264 个 map 实测 0 个带源码）。不过 map 里的 `sources` 路径（如 `../../src/llm/provider.ts`）**与 GitHub 仓库路径一一对应**，可直接 clone 对齐 |
| 结论 | **可改性高**：是在改**可读的编译产物**，不是改压缩代码。但正解是 **clone 源码 → 移植补丁进 `.ts` → 从源码构建**，不是继续改 dist |

## 三、★★ 四个扩展点（按"升级会不会失效"分层）

### A. 零改码、升级永不失效（最该用的五条）

| 扩展点 | 怎么用 | 代码证据 |
|---|---|---|
| **① modelOverrides：一个 agent 一个模型** | `inkos.json` 顶层加 `"modelOverrides": {"writer":"glm-5.3","auditor":"deepseek-v4-pro"}`。值可以是字符串（换模型）或对象（连 baseUrl/密钥/服务商一起换） | schema `models/project.js:85/:92/:117`（key 是**自由字符串，不枚举**）；唯一消费点 `pipeline/runner.js:342 resolveOverride(agentName)`；Studio 已有面板 `GET/PUT /api/v1/project/model-overrides`，UI 文案「**贵模型写正文、便宜模型审稿**」 |
| **② 审计维度开关** | 在 `story/book_rules.md` 写 `additionalAuditDimensions: ["年代考据","台词失真"]`（支持数字 id 或中英名，含模糊匹配） | `agents/continuity.js:229 buildDimensionList` → `:232-256` 读 `bookRules.additionalAuditDimensions`；schema `models/book-rules.js:34` |
| **③ SKILL.md 注入行为** | 往 `<项目根>/skills/*/SKILL.md` 或 `~/.agents/skills/*`（**你这机器上已有**）放技能，自动被 agent 加载 | `skills/external-loader.js:27 loadConfiguredAgentSkills`，扫描顺序：`INKOS_SKILL_DIRS` → `~/.openclaw/skills` → **`~/.agents/skills`** → `<项目>/​.agents/skills` → **`<项目>/skills`**（`deslop-standard` 已在用） |
| **④ webhook：每章落盘后自动触发** | `inkos.json` 的 `notify: [{type:"webhook", url, events:["chapter-complete"]}]` | 7 个事件类型（`notify/webhook.d.ts:4`），emit 点 `runner.js:782/:880/:1218/:1743`。⚠ `pipeline-error`／`diagnostic-alert` **类型里有、代码里从不 emit** |
| **⑤ 直接改真相文件** | `PUT /api/v1/books/:id/truth/:file`（任意 story 文件） | `inkos-studio/dist/api/server.js:4694`；全套 **134 个 REST 端点**，**无鉴权**，绑 localhost |

**可用 agent 名**（＝全部调用点，实测）：`architect` `writer` `auditor` `reviser` `planner` `composer` `radar` `forecast` `stateValidator`/`state-validator` `foundation-reviewer` `chapter-analyzer` `exporter` `settler` …

⚠ **两个坑**：`settler` 是**你们自己补丁造出来的** key（只在改稿/修复/同步三条路径生效，主写作路径仍硬编码 `"writer"`）；`stateValidator` 与 `state-validator` **两种拼法并存**（疑似原厂 bug），要配得配两个。

### B. 必须改码（两类）

1. **新增工具/能力**：32 个能力是 `agent/agent-tools.js` 里 32 个独立工厂函数，工具表在 `agent/agent-session.js:545 createModeTools` 按 `sessionKind` 分支硬编码（`PRODUCTION_MUTATION_TOOL_NAMES` 是一张硬编码 Set）。**没有任何 plugin/register/extend 钩子**。加工具＝改源码 + 手工插进分支数组。
2. **新增审计维度判据**：37 个维度的标签在 `agents/continuity.js:14-51 DIMENSION_LABELS`（id 1–37），判据文本在 `:85-227 buildDimensionNote`（大段内联 if）。**能开关已有维度，不能加新维度。** 阈值 `PASS_SCORE_THRESHOLD = 85` 也硬编码在 `pipeline/chapter-review-cycle.js:3`。

状态机：13 个状态（zod enum，`models/chapter.js:3`），**没有转换表、没有守卫**，状态是在各调用点直接赋值落盘的。**加新状态值＝改码。**

### C. ★ 第三条路（最干净，且完全不用碰 dist）

`inkos-core` 顶层导出了 **`PipelineRunner`** 和全部 32 个 tool 工厂（`index.d.ts:61` `export * from "./agent/index.js"`；`PipelineRunner` 在 `index.d.ts:118`）。

⇒ **可以写自己的 Node 脚本直接调 `pipeline.writeNextChapter(...)` / `pipeline.auditChapter(...)`**，绕过 Studio 和 CLI，**零补丁、升级不失效**。这是"重塑"最该走的路，而不是继续往 dist 上打补丁。

## 五、★★ 最重要的三个发现

### 发现一：**你们一直在用同一个模型写作和审计**

`auditor` 的模型选择走 `runner.js:844 → agentCtxFor("auditor")`，**无 override 时回落全局 `config.model`**——而全局是 `glm-5.3-flash`，跟写手**完全同一个模型**。

**自己写、自己审。** 温度不同（写作 0.7／审计 0.3），但模型是同一个。

`modelOverrides` 就是现成的解药，**纯配置、零代码、升级不失效**——Studio UI 里那个面板的提示文案写的就是「贵模型写正文、便宜模型审稿」。

### 发现二：**`pending_hooks.master.md` 根本不在 InkOS 里**

全量 grep `master.md` 在 core/CLI/studio 三个包 **0 命中**。InkOS 写的是 `pending_hooks.md`；**`master.md` 是 DSH 团队自己造的"主本"**，用 `cp master → pending_hooks.md` 做翻正。

**为什么造它？** 因为 InkOS 每次写章会覆盖 `pending_hooks.md`，而结算层不可靠（见补丁 4）。⇒ **你们自己发明了一个持久层，来补 InkOS 的洞。**

### 发现三：**这台机器真实的成本形状，不是"每章 30-60 分钟"，是"每章 6 个专属脚本"**

```
_fix_ch*    130 个       _bk_ch*      148 个
_ignite_ch*  52 个       _ca_*         34 个
_qr_*        31 个       其他          25+
────────────────────────────────────────
688 个脚本 / 104 章 ≈ 每章 6.6 个一次性脚本
```

**每写一章，就要现造六个脚本。** 这才是它撑不住的地方——不是墙钟时间，是**每章都要重写一遍工具**。点火单次中位 7 分钟（最长 ch97 = 30 分 30 秒），全产线点火共 9 小时 22 分；但造脚本的时间不在日志里。

**⇒ 真正的重构靶点是这个：把 688 个一次性脚本，收敛成一套参数化工具 + 声明式配置。**

而且——**`E:\work\dt-flow\`（Sep 1 23:41，含 `package.json`/`tsconfig.json`/`src`/`scripts`）是产线最后一晚留下的新工程骨架**。有人已经在朝这个方向动手了，只是没展开。同晚还有一份 `修正版SOP-写作主导权归位-20260901.md`。
