## 一、先讲清楚我理解的现状（对齐用）

**InkOS**＝生产线。npm 包 `@actalk/inkos` 1.8.0，Studio UI(4567) + CLI。它自己会：写正文 → 自动结算真相文件 → 跑审计给 overallScore → 维护状态机（drafted / ready-for-review / approved / audit-failed / state-degraded / needs-revision / imported）。**「批准」这个动作 InkOS 故意不给 AI 工具**——防 AI 给自己盖已发布章。

**书库**（`books/death-transit/`，实测 118 个章节文件）的真相层是一整套**结构化文件**：
`current_state.md`（六字段表）｜`current_state.json`（facts 带 validFrom/validUntil）｜`manifest.json`｜**`pending_hooks.master.md`（钩子池，`| H0XX | …` 表格）**｜**`chapter_summaries.md`（逐章摘要）**｜`character_matrix.md`｜`emotional_arcs.md`｜`current_focus.md`｜`author_intent.md`｜`book_rules.md`｜`outline/`｜`memory.db`(sqlite hooks 表)

**DSH 接管闭环**＝挂在 InkOS 外面的质量层，每章九步不可跳步：
点火(`node spawn detached`) → postcheck → **qr/ca 双审**（qr 载 `review` 技能、ca 载 `continuity` 技能）→ .cjs 修稿 → 簿记三件套 → 翻正四步 → 污染复核 → 终检 → 点火下一章。**每章 30-60 分钟**（点火 15 + 双审 10 + 修稿簿记 10）。

**已知痛点（都在你自己的文档里记着）**：
- ⚠ **审计 LLM 的词汇密度统计会幻觉**（报「忽然×3」实际正文 0 处）⇒ 词汇密度类必须 grep 核实
- ⚠ **结算层写的 summaries 是幻觉版** ⇒ 每章要 grep 复核、必要时 `_fix_summariesXX.cjs` 整行重写
- ⚠ **hooks 表行名漂移** ⇒ 每章要核对 db 现行行名 vs 脚本映射
- ⚠ 三层章号必须一致（「历史级翻车点」）
- ⚠ `rewrite` 模式 + 老章节 + 基线不全 = 跨章剧情污染（第 1 章事故实证）

**现成的基础设施**：
- `inkos.json` **已经有一条本地服务**：`custom:local → http://127.0.0.1:8080/v1 → qwen36`；`modelOverrides` 为空
- `style_refs/` 3 份范文绑定（乙一/张爱玲/那多），composer 自动语义选段做 few-shot
- 「创作高温记账低温」两档温度理论已落地（0.5/0.3 → 0.2/0.1）
- **`tools/zhuque-ai-detector/`（detect.py + SKILL.md）与 `tools/anti-zhuque/`（analyzer.py + prompts/）——本地朱雀工具已存在**
- 项目技能 `skills/deslop-standard/`

## 二、靶心：把 qr/ca 拆成三层，判断器只吃中间那层

现在 qr/ca 是**两个 LLM 审计任务**。逐项拆开看，它们混了三种性质完全不同的活：

| 项（来自接管方案 §六） | 该归谁 |
|---|---|
| 词频矩阵、红线词、待删词、创作术语/元词泄漏、假尾行四格式、`===END===` 工具标记、长段>300字、破折号计数、姿势/触感限额 | **脚本**（grep 更准；**而且 LLM 在这块已实证会幻觉**） |
| 已删虚构扫描、时间线算术、钩子 start_chapter 对齐、三层章号一致 | **脚本**（你已有对应 .cjs） |
| **章末收尾轮换**（与上章是否同型）／**POV 破例**／**持有物链归属**／**钩子池三态**（推进·缺失·越权）／**定板对撞**／**信息天花板合规**（机制禁量化只写定性）／**角色年龄与身份合理** | **← 判断层（可判不可算）** |
| 发现新问题、写修稿方案、改正文 | **生成层**（保留 LLM，不让判断器碰） |

**判断层的价值不在于更准，在于可以每章每段都跑**：现在一段话要问一个 LLM 要十几秒、要人读结论；判断器几秒跑完整个章节的十几道题，直接给一张带概率的表。

## 三、三层闸门（本项目的核心机制）

```
落盘
 ├─ 第一层 脚本层    可算项全绿？        ── 不绿 ⇒ 直接回修稿，不浪费后面的
 ├─ 第二层 判断层    可判项全绿？        ── 报警 ⇒ 才升到第三层
 └─ 第三层 LLM 层    双审 + captain 终裁  ── 只审被报警的部分
```

**省钱省在哪**：现在**每章都要两个 LLM 审计**（99 章 = 198 次）。有了第二层，大部分章节本地几秒扫完全绿就直接过，**只有报警的章节才上升**。省的是审计工时，不是生成工时——生成该多贵还多贵。

## 四、判断层具体判什么（第一批题单，选项都取自你现成的文件）

| # | 判断 | 题形 | 选项/参照来自 |
|---|---|---|---|
| 1 | 这段的持有物在谁手上？与正典一致吗 | Choice（角色名）＋ Noul | `current_state.md` 持有链 |
| 2 | 本章推进了哪个钩子？ | Choice（H0XX 清单） | `pending_hooks.master.md` |
| 3 | 本章有没有**越权掀**某个「暂不掀」的钩子？ | Noul 逐条 | 本章 ctx §二 |
| 4 | 这段碰了哪条书级红线？ | Choice（红线条目） | `story/book_rules.md` + 交接文档定板节 |
| 5 | 这段把机制量化了吗？（信息天花板） | Noul | 定板「机制禁量化」 |
| 6 | 章末收尾与上章同型吗？ | Choice（收尾类型） | 上章末 + 收尾基线候选句 |
| 7 | 这段属于 POV 破例吗？ | Noul | ctx §九 POV 限额 |
| 8 | **结算层写的这行 summary 与正文一致吗？** | Noul | 正文 vs `chapter_summaries.md` |
| 9 | 这个角色的行为与他的人设一致吗？ | Noul | `character_matrix.md` |

**第 8 条是现成痛点**——你每章都要人工 grep 复核结算层的幻觉版 summaries。判断器把它变成自动比对。

**★ 关键架构点**：判断器读不了 99 章，但 `chapter_summaries.md` **天然就是长上下文压缩层**。所以跨章判断的正确输入是「**全书 summaries ＋ 本章正文**」，不是全书正文。这套文件结构正好喂得上。

## 五、跨章层（第一批题单跑顺之后）

1. **全书钩子回收审计**：99 章的钩子池 → 哪些埋了没收、哪些凭空回收。**你 horror-teller 那边的「伏笔回收图谱」格式（埋设位置+原文｜回收位置+原文｜功能）比 `pending_hooks.master.md` 更结构化，可以直接移植成 99 章的图谱。**
2. **节奏曲线**：每章一组分数 → 钩子强度/情绪涨落沿章号的线。**《死亡换乘》99 章下来一张图**，正好用来定第三卷的节奏基线。
3. **角色漂移**：逐角色问「这一章的他和前 20 章的他一致吗」。

## 七、★ 最大胆的一条：把「定板」变成可执行、可统计的判断

你现在有书级红线/定板（锚日语义、已删虚构清单、持有链禁令、信息天花板、词频红线、禁创作术语）。**它们今天活在交接文档的散文里 + ctx 的硬规段里**，ca 做「定板对撞」靠 LLM 读。

判断层可以把**每一条定板变成一道 typed question，每章跑一次**。两个后果：

1. **定板从「人想起来才查」变成「每章机器必查」**，且不再依赖 LLM 当次读得细不细。
2. **每条定板会积累自己的命中率**——哪条定板从没被触发过（可能是死规则），哪条经常被碰（说明写手总踩、ctx 没写清）。

第 2 条才是真东西：**这跟你预测项目里「度量先验分辨力」是同一个动作**——先看哪条规则真的在起作用，再决定留哪条。**规则没被用过，跟规则不存在，对生产线是同一件事。**

## 八、必须先解决的一个配置问题

你那批判据里有**三条互相打架的**（跨 horror-teller 与 InkOS 两边技能）：
- **破折号**：humanizer-zh 的某些作者腔允许并鼓励 vs 其余要求清零
- **引号**：novel-humanize 强制「」 vs deslop 明令禁「」 vs humanizer-zh 默认 ""
- **精确数字**：novel-humanize 把精确数字列为 AI 铁证要体感化 vs horror-teller 硬规 7 要求「数字精确、地名模糊」

**判断题库上线前必须按 profile 分叉**（口播稿／网文正文／非虚构），否则同一个模型第二天就会给你自相矛盾的结论。

## 九、明确不做

1. **不让判断器管词频统计**——grep 更准，而且**你已经实证过 LLM 在这块会幻觉**。别把确定性的事换成概率。
2. **不让它写正文或改稿**——它不生成文字。它只做前置筛选，改稿仍归 InkOS `revise` 通道 + LLM。
3. **不让它替代「批准」**——那是 InkOS 刻意留给人唯一的动作。
4. **不让它做需要跨全书长推理的事**——用 `chapter_summaries.md` 压缩层绕开，别硬塞 99 章。

## 十、开工前必须核实的一条（决定项目形态）

`inkos.json` 的 `modelOverrides` 是空的，**我不知道 InkOS 是否原生支持「不同任务用不同模型」**（例如审计/判断走本地小模型、创作走 step/glm）。

- **支持** ⇒ 判断层可以长在 InkOS **里面**，是配置级接入（`custom:local` 那条现成的服务就能用）
- **不支持** ⇒ 判断层只能像现在的 qr/ca 一样**挂在 DSH 闭环外面**，作为独立预检脚本

这两种形态的工作量差很多，**所以这是第一件要查的事**。
