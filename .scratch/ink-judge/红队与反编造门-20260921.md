## 二、独立事前验尸：假设半年后失败了，为什么

### 按概率排序的失败路径

**P1 · 产线已停：优化一台吞吐为 0 的机器**（最高概率）
判断层的全部价值挂在"每章省两次审计"，而收益 = 单章节省 × 章节产量。**产量为 0 时收益为 0，与判断层多准无关。**
证据：该书最后活动 **2026-09-01 23:48**，今天 09-21，**空转 20 天**；停在 104 章；`E:\小说工坊\` 0 个 .cjs。
⚠ **缺「为什么停了」这个事实**：放假／完本／弃坑／已转向恐怖口播——三种可能后果完全不同。但**无论哪种都不构成"现在开工"的理由**。

**P2 · 「省审计工时」没算过，而且误差方向被设计反了**
判断层前置 ⇒ 它有两种错：**漏报**（有问题的章判绿 → 问题被簿记三件套固化，k 章后才发现）与**误报**（好章判红 → 只多跑一次 LLM，可忽略）。
**唯一便宜的错误是保守，但产品叙事卖的是放行。** 要压低漏报率，阈值必须极保守，放行率随之崩塌。
证据：无打回率数据；InkOS 缺陷①②正是"审计/结算层产出看起来合理但是假的"这一类 ⇒ 漏报在这条线上**不是理论风险，是已发生过的缺陷类别**。

**P3 · AND 门的放大效应**（纯结构推理，与具体数值无关）
九项全绿才升级 = AND 门。若每项准确率 0.9（对未经第三方验证的小模型已是乐观值），联合放行率 ≈ **0.9⁹ ≈ 0.39** ⇒ 六成章节照样上升 LLM，一半以上收益消失。改成"任一项红才升级"则漏报率立刻翻上来，退回 P2。**这是一个没有调节旋钮的设计。**

**P4 · 输入放不下，且与已有本地服务抢显存**
8 GiB 要与 `127.0.0.1:8080` 上的 qwen36 **共存**；torch 未装、E: 剩 34G。跑得通之后上下文被压到最小 ⇒ 要么塞不进「整章 + 钩子清单 + 角色表」，要么砍 few-shot——而 0.8B 级模型没 few-shot 基本不工作。
★ **性质判断**：缺陷①说明大模型连**计数**都做不好，提案正确地把计数推给脚本，却把**比计数更难**的任务（谁持有、推进了哪个钩子）推给更小的模型。**「能不能 grep」和「小模型能不能做」是两根正交的轴，我把它们压成了一根——这是设计的核心错误。**

**P5 · 选项空间过大 + 极度不平衡 ⇒ 上线后退化成「一律答没事」**
「持有物在谁手上」选项可能是几十个角色名；「推进了哪个钩子」的 ID 形如 `H-017` 无语义，必须读描述才能选。更致命：「碰了哪条红线」「有没有越权掀钩子」是**低频事件**——大多数章不碰，于是**「一律答没碰」的自测准确率就极高**。
这正是本项目在预测线上反复吃过的亏：**常数臂／零分辨力度量／构造性读数**（`v3_baserate` 是常数臂、40/40 全同值、相关由构造为 0）。**换到小说线，同一个坑换了张脸。**
附带伤：题单里 ⑤「机制有没有被量化」与 ⑥「章末收尾与上章同型」**大概率脚本就能做** ⇒ 证明我的三分法在自己的题单上就没被严格执行。
另：缺陷③ hooks 表行名会漂移 ⇒ **选项清单本身不稳定**，用旧漂移态做的标注会与当前 ID 对不上。

**P6 · 校准真值是循环论证，而且部署会吃掉自己的标注**（四条独立循环）
(a) **只有正样本**（被打回/被终裁改过），没有负样本 ⇒ 只能算"能不能复现 qr/ca 的打回"，**算不出漏报率**；
(b) **标签由被替代的系统产出**，而该系统已实证会幻觉（缺陷①）⇒ 测的是"与一个已知不可靠 oracle 的一致率"；
(c) **只有一个分布**（一本书、一类、一个声音）⇒ 成功了也只能推广到第 105 章；
(d) ★ **部署即毁标注**：判断层一旦前置拦截，qr/ca 就再也看不见被放行的章节 ⇒ **正样本停止产生**；此后只有"判断层拿不准而升级"的章节会被标注，标注集偏向判断层的困惑区 ⇒ **后续校准全部有偏**。
⚠ 最危险的下游动作：把定板逐条变判断题、积累命中率、"从未触发=死规则"⇒ **用未验证的仪器生产删除依据**，在一个已出过跨章污染事故（缺陷④）的系统上删红线。

**P7 · 第四张嘴，没有仲裁者，且与系统自设原则正面冲突**（最硬的一条）
现在已有 InkOS 自带审计（给分）、qr/ca 双审、captain 终裁——三条口径。加入后，放行路径上的事实终裁者变成判断层（它说绿，qr/ca 看不到这一章），而它是最不可问责的一个：**没有理由、没有依据、连校准集都来自它取代的那个系统。**
★ **证据（这条最硬）**：材料原文写着 InkOS「**故意不把『批准』这个动作交给 AI**」（防 AI 自己给自己盖已发布章）。而我的设计「全绿即放行」——**就是把这个动作交给了 AI，只是套了个阈值的外衣**。这不是实现细节偏差，是**与系统设计意图的直接冲突**。
附加：把 qr/ca 的活分派给「脚本/判断层/LLM」三类的**分派者是谁**？一次划定就冻结且必然有错；逐条划则需要第四个仲裁者。提案没给分派规则。

**P8 · 没有插入点，也没有归属**
九步闭环目前可见证据只有文档描述，执行它的 .cjs 不在 `E:\小说工坊\`。没有单一入口就没有插桩点，只能改人的操作习惯；**人在赶稿时会跳过步骤，尤其跳过"新加的、慢的那个"** ⇒ 半年后变成一个没人跑的可选脚本。

**P9 · 范围蔓延：人味参照与素材库不服务"验证"这个目标**
39 份 ASR 是"生成风格参照"，453 篇怪谈+127 张卡是"创作素材"。塞进判断层 few-shot 既撑爆上下文（放大 P4），又把判断题从"按题单判"漂移成"像不像人写的"——**一个没有金标准的软判断**。半年后的评估报告里会出现一堆关于"人味"的讨论，而九项题单无人过问。

### 最经不起问的一条

**「能省掉大部分章节的两次 LLM 审计。」**
它是全案唯一正当性来源，却一个数都没给；而且同时具备两个独立致命伤——**结构上**九项 AND 门放行率天生很低（P3），**方向上**漏报是这条线上唯一昂贵且会入账的错误，而设计恰把判断层放在最需要保守的位置上做放行（P2）。

> **能问死它的一句话：过去 104 章里，有多少章的 qr/ca 是首轮全绿、一次都不用修稿的？**
> 这一个数就是收益的天花板；拿不出来，提案没有可讨论的基础。

## 三、修正后的结论：不该做 → 改成什么再做

**不该做**——不是技术上行不通，而是**三个前提同时不成立**：要优化的量（审计工时）从未被测过；要服务的产线已停摆 20 天；放行式设计与系统「批准不交给 AI」的自设原则冲突。

**改成这样再做**（按顺序，前一步不通过就不做下一步）：

1. **先测，不先建。** 今天就能取的三个数：本周实际产能（章/周）、过去若干章 qr/ca 的**打回率**、每章 30-60 分钟里「LLM 审计」与「人工复核」各占多少。打回率直接给出收益天花板；若 LLM 审计在每章墙钟里占比很低，**提案当场作废**。
2. **先交付确定性的那一半。** 把四类已知缺陷里可机械检查的做成脚本：统计类检查（治词频幻觉）、hooks 行名规范化（治漂移）、摘要与正文的可计算对齐、跨章引用边界。**零模型、零校准、收益确定。** 提案自己承认"能 grep 的该归脚本"——那就先把它交出来。
3. **★ 判断层若还做：砍到一两个任务，并且只能升级、不能放行。**
   它的输出只允许是「这章需要 LLM 审计」，**永不允许是「这章可以跳过」**。这样它在结构上**不可能造成漏报事故**，也保住了「批准不交给 AI」。收益叙事随之改写为「**提前定位问题、缩短修稿循环**」——**这个收益即使放行率为 0 也成立。**
4. **「死规则」只报告、不删除**，且报告必须同时给出检测器自身的漏报率作为混杂项。
5. **验收用漏报率（人工抽查的负样本），不用自测准确率**；没有独立第三方验证前，任何"准确率"数字不进决策。
