### 2.2 KV cache

```
KV 字节 = 2(K与V) × n_kv层数 × n_kv_heads × head_dim × dtype字节 × 序列长度
```

`n_kv层数` **不等于** `num_hidden_layers`——只算**带 KV 的注意力层**。这是本机落地判断里最容易算错的一项，因为 Qwen3.5 家族是混合架构。

| 模型 | 注意力类型 | n_kv层 | n_kv_heads | head_dim | **B/token** | @512 tok | @8192 tok |
|---|---|---|---|---|---|---|---|
| 0.421B laya | **编码器（双向，无 KV）** | 0 | — | — | **0** | 0 | 0 |
| 0.151B rlcd-modernbert | **编码器（双向，无 KV）** | 0 | — | — | **0** | 0 | 0 |
| 0.752B Qwen3-0.6B | dense | 28 | 8 | 128 | **114,688** ＝ 112.0 KiB | 56 MiB | 0.88 GiB |
| 1.107B PlayJev-0.8B | hybrid（每 4 层 1 层 full） | 6 | 2 | 256 | **12,288** ＝ 12.0 KiB | 6 MiB | 0.09 GiB |
| 2.274B Qwen3.5-2B | hybrid | 6 | 2 | 256 | **12,288** ＝ 12.0 KiB | 6 MiB | 0.09 GiB |
| 4.022B Qwen3-4B | dense | 36 | 8 | 128 | **147,456** ＝ 144.0 KiB | 72 MiB | 1.12 GiB |
| 8.191B Qwen3-8B | dense | 36 | 8 | 128 | **147,456** ＝ 144.0 KiB | 72 MiB | 1.12 GiB |
| 9.653B Qwen3.5-9B | hybrid（32 层中 8 层 full） | 8 | 4 | 256 | **32,768** ＝ 32.0 KiB | 16 MiB | 0.25 GiB |

**三个必须记住的结论**：
1. **编码器类（Laya / rlcd-modernbert）KV ＝ 0。** 它们是 non-autoregressive（非自回归），整段前缀**一次前向算完**，没有逐 token 增长的 cache。这是它们在 8 GiB 机器上最本质的优势，比「参数小」重要得多。
2. **混合线性注意力（Qwen3.5 家族 / PlayJev）比 dense 省 ~10×**：12 KiB/token vs 112–144 KiB/token。因为 `layer_types` 里 3/4 是 `linear_attention`（Mamba 式），**状态不随序列增长**（O(1)），只有那 1/4 的 `full_attention` 层建 KV。
3. **dense 解码器的 KV 是真成本**：Qwen3-8B 在 8192 tok 时要 1.12 GiB——这刚好是它权重之外压垮 6.6 GiB 预算的东西。

> 数据来源：`layer_types` / `num_key_value_heads` / `head_dim` 全部由我本次 HTTP 取 `config.json` 读得（URL 与字段见 §3 末）。

### 2.3 激活量

两类，量级差很大：

**(a) 逐层张量（H×seq×dtype）** —— 小到可忽略：

```
单张量 = batch × seq × hidden × dtype字节
laya @512, hidden=1024, F16: 1 × 512 × 1024 × 2 = 1.0 MiB
```
峰值同时活跃约 10–20 个张量 ⟹ **十几 MiB 量级**。在 6.6 GiB 面前是噪声。

**(b) 注意力分数矩阵（heads×seq²×dtype）** —— 这一项会**爆炸**，是长上下文 prefill 的真正杀手：

```
注意力矩阵 = batch × n_heads × seq² × dtype字节
```

| 场景 | 算式 | 结果 |
|---|---|---|
| laya @512（16 头） | 16 × 512² × 2 | 8.0 MiB |
| laya-multilingual @1024（16 头） | 16 × 1024² × 2 | 32.0 MiB |
| Qwen3-8B prefill @4096（32 头） | 32 × 4096² × 2 | **1024 MiB** |
| Qwen3-8B prefill @8192（32 头） | 32 × 8192² × 2 | **4.00 GiB** |
| Qwen3.5 标称上限 262144 | 16 × 262144² × 2 | **2048 GiB（纯理论，必用 FlashAttention 才可能）** |

**落地含义**：本机若要跑 dense 解码器，**必须走 FlashAttention/SDPA**（否则 4k 上下文就吃掉 1 GiB 显存、8k 直接爆）。而 **Laya 这类编码器 seq 上限只有 512–1024，注意力矩阵 ≤32 MiB，压根不构成问题**；混合线性注意力层更没有 seq² 项。再叠上 Laya 的 `local_attention: 128`（2/3 层走滑窗）+ `max_position_embeddings: 8192`，它的激活面是被结构性锁死的。

## 4. 实测吞吐（本机真跑，不是估算）

全部用本机已装的 Ollama 0.32.4 在 RTX 4060 Laptop 上跑出来，`ollama ps` + `nvidia-smi` 双证设备归属。

| 模型 / 姿态 | 设备（`ollama ps` 实测） | 指标 | **实测值** |
|---|---|---|---|
| `qwen3-vl:8b` 8.8B Q4_K_M | **20%/80% CPU/GPU** | 冷加载 | **8.90 s** |
| 同上 | 同上 | 解码（128 tok / 5.497 s） | **23.29 tok/s** |
| 同上 | 同上 | **prefill（7014 tok / 6.143 s）** | **1141.82 tok/s** |
| `glm-ocr` 1.1B F16 | **100% GPU** | 冷加载 | 3.46 s |
| 同上 | 同上 | 解码（96 tok） | **128.36 tok/s** |
| `qwen3-embedding:0.6b` 0.752B Q8_0 | **100% GPU** | **单次前向 277 tok**（3 次） | **38.8 / 41.3 / 27.3 ms**（中位 ≈38.8 ms） |
| 同上 | **100% CPU**（强制 `num_gpu:0`，逐次 `ollama ps` 验） | 单次前向 16 tok（2 次） | **36.2 / 35.5 ms** ⟹ **≈2.22 ms/token** |

**由此得到的本机常量**：

```
GPU 单次前向（0.752B 级，Q8_0）  ≈ 0.140 ms/token   （38.8 ms ÷ 277 tok）
CPU 单次前向（同模型，同输入）     ≈ 2.22  ms/token   （35.5 ms ÷ 16 tok）
                                ⟹ CPU/GPU ≈ 16×
```

**外推到 Laya（421M 编码器、512 tok 预算）**：
```
0.140 ms/token × (421.3M ÷ 751.6M) × 512 tok ≈ 40 ms
```
对照组：Laya README □厂商宣称 在 Tesla T4 上「Latency, 1 question (T4 GPU) = **39.5 ms**」。**我的实测外推 40 ms 与它的宣称 39.5 ms 落在同一个点上**——这是我对 Laya 延迟宣称的可信度评级从「未核」升到「本机量级可信」的依据。

**CPU 兜底的真实代价**：把同一个 0.752B 模型推到 CPU，per-token 成本从 0.140 ms 涨到 2.22 ms（**16×**）。折成 Laya 的 512 tok 一问：CPU 外推 `2.22 × (421.3/751.6) × 512 ≈ 636 ms/问`。Laya README □厂商宣称 CPU 是「193–464 ms」——**我实测外推比它宣称慢 1.4–3.3×**。这个差我不去抹平，原样报出：可能是它的 CPU 有 AVX-512 / 服务级 CPU，也可能是宣称偏乐观，我没有条件分辨。

## 5. Windows 工程路径与坑（**本节只查与算，未安装任何东西**）

### 5.1 vLLM：Windows 原生**官方明确不支持**，WSL 是被点名的路径

**不是传闻，是它自己 `setup.py` 里的硬编码判断**（本次 `curl -sS https://raw.githubusercontent.com/vllm-project/vllm/main/setup.py`，HTTP 200，60,345 B，`grep -n`）：

```
100:elif not (sys.platform.startswith("linux") or sys.platform.startswith("darwin")):
101:    logger.warning(
102:        "vLLM only supports Linux platform (including WSL) and MacOS."
103:        "Building on %s, "
104:        "so vLLM may not be able to run correctly",
105:        sys.platform,
106:    )
107:    VLLM_TARGET_DEVICE = "empty"
```

**读法**：只要平台既不是 Linux 也不是 macOS（Windows 就是），vLLM **自己把 `VLLM_TARGET_DEVICE` 设成 `"empty"`** 并警告「可能无法正确运行」。官方原文点名 **「Linux platform (including WSL)」** —— 即 **WSL 是官方认可的 Windows 落地路径，原生 Windows 不是**。

**PyPI 侧独立佐证（我实际查的包数据）**：
```
vllm latest = 0.29.0 | requires_python = <3.15,>=3.10
files for latest release: 只有 2 个 manylinux wheel + 1 个 sdist
any windows wheel? False
--- all win wheels across ALL releases ---
  windows wheels = 0 / total files = 297
```
**全部 297 个历史发布文件里，Windows wheel 数量为 0。** 所以 `pip install vllm` 在 Windows 上拿不到二进制，只能落到 sdist 源码编译，而源码里 `VLLM_TARGET_DEVICE="empty"` 已经判了它「可能无法正确运行」。**结论：Windows 原生 vLLM ＝ 不要走。**

**WSL2 在本机的真实状况（★亲测，这是个坑）**：
```
$ wsl -l -v
  NAME              STATE      VERSION
* Ubuntu-24.04     Stopped    2
  docker-desktop   Running    2

$ wsl -d Ubuntu-24.04 -- nvidia-smi -L
Exit code 127
... WSL2: 系统找不到指定的路径。
错误代码: Wsl/Service/CreateInstance/MountDisk/HCS/ERROR_PATH_NOT_FOUND
```
指向的 `C:\Users\crx\AppData\Local\wsl\{302cb1d5-...}\ext4.vhdx` —— 我列了 `C:\Users\crx\AppData\Local\wsl\` 目录，**是空的**。即 **Ubuntu-24.04 是一个残留注册项，磁盘镜像已不存在**。所以：
- WSL2 **功能在**（`docker-desktop` 发行版正在运行，Docker Desktop 4.82.0 可用）；
- 但**现成的 Ubuntu 发行版起不来**，要真用 WSL 跑 vLLM，得先重装发行版（`wsl --install` 之类）——**这属于「要改动系统」，本次硬约束不允许我做，所以我没做，也无法验证 WSL2 里 GPU 直通是否可用**（标记：**未核**）。
- 结论：走 vLLM 的路 = 先修 WSL + 拉 CUDA base 镜像（~100 MB+）+ 装 vLLM，**这不叫「最小」**。

### 5.3 Ollama：**本机已经装好并在跑，这是最便宜的路**

## 7. 跑通后怎么变成 Node 能调的 HTTP 端点（本项目脚本都是 Node）

```
┌──────────────┐   fetch('http://127.0.0.1:PORT/decide', {method:'POST'})   ┌────────────────┐
│ Node 脚本     │ ────────────────────────────────────────────────────────▶ │ Python 服务     │
│ (p1b/*.cjs)  │                                                           │ uvicorn:PORT   │
└──────────────┘ ◀──────────────────────────────────────────────────────── └────────────────┘
                    {answers:{q:{choice, probabilities, confidence}}}
```

三条可选后端，端口不同、契约可统一：

| 后端 | 端 | 起法 | Node 侧 |
|---|---|---|---|
| **Ollama**（已跑） | `http://127.0.0.1:11434` | 已在跑 | 直接 `fetch('/v1/chat/completions')`，`logprobs` 取选项概率 |
| **ONNX/CPU 服务**（方案 A） | 自选，如 `127.0.0.1:8790` | `uvicorn wrapper:app --port 8790` | `fetch` POST JSON |
| **Laya 服务**（方案 B） | 自选，如 `127.0.0.1:8791` | `uvicorn laya_api:app --port 8791` | 同上 |

**接线要点**：
1. **端口必须显式避开 8787**（本项目铁律 ⑨「8787 零接触」）。上表我特意选 8790/8791。
2. **服务只绑 127.0.0.1**（铁律 ⑤ key 不出服务端；本地推理服务同理，不要 `0.0.0.0`）。
3. **Node 侧只依赖内建 `fetch`**（v24 有），不引入 npm 包 ⟹ 不违反「禁 npm i」。
4. **一次请求 = 一次完整前向**是这类模型的天然形态（Laya「Every question in a call is answered in one single forward pass」□厂商宣称），所以 Node 侧应该**把一批问题打包成一次 POST**，而不是每条问题一次往返——这跟本机实测的「prefill 是瓶颈」完全一致：prefill 1141.82 tok/s，多问几个的边际成本远低于重新 prefill。
5. **超时预算**：按本机实测给——Laya GPU ≈ 40 ms/问；CPU ≈ 636 ms/问；若 state 到 7k token 且模型是 8.8B 级，**prefill 单项就 6.14 s**（实测）。Node 的 `AbortSignal.timeout()` 建议不低于 30 s。

**写 wrapper 时不要引的依赖**：`torch` 之外的都不需要（`fastapi`/`uvicorn`/`pydantic` 已装）。

## 10. 敢说不（本项目的纪律：说「不该做」和说「该做」一样有价值）

1. **不该为这件事修 WSL、不该碰 vLLM。** 本机已经有一个跑着的 Ollama 和一个 8.8B Q4 模型实测跑通；要跑的目标最大的一个是 421M 的编码器（0.785 GiB）。**为 0.785 GiB 的模型去动系统装 Linux 子系统，是把简单问题做复杂。**
2. **8 GiB 这台机器真正跑得舒服的天花板，我实测画出来是「权重 ≤ 3–4 GiB」。** 证据不是推导：`qwen3-vl:8b` 的 **5.72 GiB 权重就已经被拆到 CPU（20%）**；`qwen3-embedding:0.6b` 的 0.85 GiB 权重 + 8k KV 也只有 100% GPU 勉强。所以：**2.274B 及以下 F16 舒适，4.022B F16 直接出局，9.653B 全姿态出局。**
3. **本批里唯一「零安装、几百 MiB、一定放得下」的是第 15 条（rlcd-modernbert-151m）——但它有 25 选项的硬顶。** 如果下游方案依赖 Jev 的「最多 255 选项 Choice」，那么**这一条在能力上就不合格**，再便宜也没用。
4. **技术上与本机最匹配的是 Laya（第 23 条）**：编码器 ⟹ KV ＝ 0；421M ⟹ 权重 0.785 GiB ⟹ 显存能同时放 3 个；延迟外推 40 ms 与厂商宣称吻合。**它唯一的实际成本是 `torch`（CUDA 版 2.42 GiB 下载，实测 4.6 分钟）。** 若非要在这批里选一个真跑的，我选它——但**这个「选」是工程匹配度，不是准确度认可**（准确度我没复现，见 §9.6）。
5. **一个必须往上递的工程事实**：本机 **prefill 才是瓶颈**（实测 1141.82 tok/s @8.8B）。「一次 prefill 答多题」这类架构在**大 state、小模型**时非常划算，在**大 state、大模型**时会被 prefill 吃掉全部预算（7k token state ≈ 6.14 s）。所以集成方案里 **state 的表达方式**（塞多少 token）比**选哪个模型**更决定延迟。这条是我实测数字直接支持的，不是推测。
