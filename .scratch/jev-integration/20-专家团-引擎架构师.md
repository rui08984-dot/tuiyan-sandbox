## 0. 立场

**条件放行 —— 但放行的只是「一次冗余判死测」，不是「整合」。**

拆成四句，每句都给判定：

1. **作为第 7 层（L7）进引擎：不该做。** 唯一堵点是 `predictions.layer` 的 CHECK 枚举，而堵它的那张表是本项目**明文不可变**的账本（铁律⑦）。为一个外部模型去重建账本表，是拿最不可逆的资产换最不必要的东西。
2. **作为某层的替代实现（换掉 L2/L3 的引擎）：不该做。** 它会把「先验层」改成「读数列」，直接改掉 1005 行配对的生产读数与 Bayesian 语义登记——而且没有任何证据表明换上去会更准（见 §4）。
3. **作为挑战者臂（读侧影子）：这是唯一正确的引擎内身份，但必须排在判死测之后。** 脚手架确实是现成的、可复用的（判据机、walk-forward、TOST/MDE/Holm、C0 阴性对照、`--arms` 开跑令闸），但**臂定义改动＝PREREG 版本递进**，不是免费加一行。
4. **作为旁路读数（根本不进引擎）：这才是第一步该有的形态。** 零迁移、零账本写、零引擎槽位改动，代价是「没有判据、只有数」。

**一句话**：问「能不能整合进引擎」，我的回答是**不能**（四个更重的身份我全部判否）；问「值不值得拿一次读侧测量把它判生判死」，我的回答是**值得，而且必须现在做**——因为这个项目**自己已经把这件事写成了待办**（§3）。

### 2.1 三条从源码里读出来的、产物没说的机制事实

**（甲）外部模型**不能**当 `p1b/src/engines/` 里的引擎——不是纪律问题，是**函数形状**问题。**
`e2-combo-precheck.cjs:96-101` require 六个引擎模块，`:147-153` 逐个调用：

```js
const o2 = l2Baseline({ baseRate: st, baseRateNote: r.brn }); if (o2 && o2.ok) eng.L2 = o2.p;
```

全部是**同步纯函数，输入只来自该行与它所在局**；而 `buildEngineMatrix` 本身是一个 1532 行的同步循环、零 I/O。一个外部模型（托管 API 或本机服务）是**异步 I/O ＋ 非确定性**。这不是「加一行 require」能解决的。

⇒ **唯一可行的机制是「制件」：模型只在生成工件时出现一次，引擎只吃 sha 冻结的工件。** 即

```
候选源（托管/本地/甚至人工）─▶ 一次性跑出 {question_id → p} 工件 ＋ sha256
                                        │
                          p1b/src/engines/<name>.js  ← 纯函数，只读工件（零网络）
```

这条改法有**盘上先例**：L5 的认证源不是运行时查询，而是读侧注册表重建（`l5_sources.js`，02 §A.2 实测 108 行）；真值口径缺陷用指纹 `78b8cedb9d37307a…` 固化（02 §A.2）。**同一个模式。**

**顺带解决一个硬伤**：10 号件 §7.1 指出 hosted Jev「`jev-latest` 别名会移动、限流动态、版本会漂」，即**复算不可复现**；而本项目的 walk-forward 骨架要求「同输入逐字节同」（转引 03 §5-G4）。把模型降级为「制件时出现一次」，**版本漂移就再也伤不到读数**——读的是冻结工件，不是活 API。这是我认为这个方案唯一真正的架构价值。

**（乙）02 号件说 `makeKnnArm` 是「把外部特征变成可替换臂的现成工厂函数」——这句要改。** 我逐行读了 `thickcell-replay.cjs:76-103`：

```js
function makeKnnArm(kappa) {                 // :76
  return function knnArm(ctx, q) { ... }     // :77
}
DECLARED_ARMS.knn.impl = makeKnnArm(KNN_KAPPA);   // :104
```

`makeKnnArm` 的**唯一参数是 κ（kNN 的距离权重）**，函数体里 `KNN_K`（`:56` k=30）、四维向量 `[sin,cos,lat,lon]`（`:82`）、四对 `PAIR_KINDS`（`:60-65`）全部写死。**它是 kNN 专用工厂，不是通用注入器。**
真正通用的缝有两条，且比 02 说的更朴素：
- **`replayCell(rows, armFn)`（`:181`）** —— 接受任意 `armFn`。`:74` 注释逐字：「臂签名与其它臂一致＝`(ctx, q) → p`」。**这才是缝。**
- **`DECLARED_ARMS` 注册表（`:68-73`）** —— 四项 `mos`/`nowcast`/`granger_lag`/`knn` 的 note 里逐条写着「PREREG §4」。**往这里加第 5 项＝改 PREREG §4 的臂清单＝版本递进。**

另外我读到两个 02 未提的**免费资产**：`:108-111` 的 `SELFTEST_ARMS`（`identity` 臂「臂≡基线 ⇒ Δ≡0、σ̂_d=0」＋`const_half` 对照臂）——即**仪器自检是现成的**；`:171-177` 的 `knnPool` 强制「四维特征缺一则该题不入臂（禁缺维硬算）」。

**（丙）「下游自动继承」与「不扰动已收口负结果的复算输入」是互斥的——必须二选一。**
02 号件 §C.1 把「新源顺带进 `e2-r1-rules.cjs`／`dna-s-judge.cjs`／`thickcell-replay.cjs`／`a1-whatif.cjs` 四个下游」当成**好处**。但看我亲读的调用点：`thickcell-replay.cjs:115-116`

```js
const M = require(path.join(ROOT, 'p1b', 'scripts', 'e2-combo-precheck.cjs'));
const mat = M.buildEngineMatrix(dbPath);          // 复用同一实现：池/域/引擎读数一律取自此
```

`buildPool` 是厚格四件 PREREG 点名的**唯一复算入口**；`:124` 的 `base: Number(r.eng[r.layer])` 直接取该行本层引擎读数。而 `buildEngineMatrix` 头注（`:93`）逐字：「★单一实现：R1 审计件 `e2-r1-rules.cjs` 直接 require 本函数，**禁写第二份**」。

⇒ 若**原地改** `:139` 的 `ENGINE_KEYS`，四条下游的输入同时变——其中包括**已收口负结果 H6（E2 路由全灭）**的复算输入。账本里的负结果账本有「复算入口（路径＋sha16）」四要素纪律（转引 01 §5.1），**改这个函数等于让那个复算入口不再逐字节可复现**。

⇒ 正确的做法是**参数化而非原地改**：`buildEngineMatrix(dbPath, extraEngines = null)`。默认行为逐字节不变 ⇒ 全部现存调用点（我 grep 到的 7 处：`e2-r1-rules.cjs:62,125`／`e2-shadow-score.cjs:370`／`thickcell-replay.cjs:115,229`／`a1-whatif.cjs:175`／`dna-s-judge.cjs:58`／`role3-combiner.cjs:116`）**一行都不用动**。代价是：新源**不会**自动流进那四个下游——而这正是我要的（第一步只做判死，不惊动任何已收口的东西）。

## 4. 正面回应本项目的「加一个模型」负结果史

本项目的存量是 **15 条有据可查的死路**（11 条实证 H1–H11 ＋ 4 条设计层拒绝 D1–D4，转引 01 §5.1 读 `p1b/sim/out/negative-results-ledger-20260920.json`）。逐条对位，不许含糊：

| 负结果 | 它是什么形状 | 对本案的直接含义 |
|---|---|---|
| **H5 校准挑战者 beta calibration** | 加一个挑战者 → **未达非劣** → 维持恒等 | **同一个判据机（C1 非劣）+ 同一堵功效墙**。见下方 §4.1 的算术 |
| **H6 E2 路由 R3a/R3h** | 在既有引擎上加路由臂 → **全灭** | 我 §2.1(丙) 说的「不要原地改 `buildEngineMatrix`」正是为了**不扰动 H6 的复算入口** |
| **H7「D2 回测 model 臂（第一版模型）」** | 加一个 model 臂 → **model ≡ base** | **最像的一条**。我的回答见 §4.2 |
| **H10 E1·DNA 加列制 S 维** | 加一列特征 → 线终止 | 特征类增量的先例 |
| **H11 厚格 Granger** | 需要序列历史值 → **账本不存序列值 ⇒ 不可估 ⇒ 封存** | **本案不能重演**：外部模型的输入若也是「账本没存的东西」（例如每局的完整 state），会撞同一堵墙（见 §5.3） |
| **角色③ 分支合成器** | 新臂 → Δ=−0.008787 MDE=0.044270，**C1 未证立，判非劣需 n≈4704（现 60）** | **姿态先例**：维持「**只披露**」、不入在役判据 |
| **H1 命题 A** | 消融 → Δ=+0.00299＜0.02，止发「**勿复跑**」 | 本项目对「差一点点」的处理是先例：止发 |
| 第 8 次同族形态 | 「离散度 vs 位置」主导差异在离散度（01 §5.3-2 引锚 p29:30） | 新臂的 Δ 也可能同样被离散度主导，而非被能力主导 |

### 4.1 功效算术：这个臂**结构上**够不到本项目自己的非劣边际

不改判据、不新造阈值，就用盘上现成口径算：

- 本项目非劣主判据＝配对 ΔBrier 95%CI **上界 ≤ +0.005**（转引 03 §5-G3）。
- MDE 口径 `2.802·σ̂_d/√n`（`e2-shadow-score.cjs:134-135`，我 grep 到定义；`role3-combiner.cjs:139` 等处为 2.8 同式重写——02 §B.3 登记过这处 0.07% 口径差）。
- 角色③ 的实测标定：MDE=0.044270 @ n=60 ⇒ `σ̂_d = 0.04427×√60/2.802 ≈ 0.1224`。
- 把这把尺拿到 L2 的可计分人口（`scored_n=385`，转引 01 §2.2）：`MDE = 2.802×0.1224/√385 ≈ 0.0175` —— **是本项目非劣边际的 3.5 倍**。

⇒ **即使外部源在 L2 行上完全不输，C1 也会因 CI 太宽而「未证立」**，与角色③ 同一个死法（角色③ 需 n≈4704 才够，L2 的 385 只到它的 **8%**）。**这不是我的悲观，是盘上两个既有数字相乘的结果**，且我没有假设新源更差。

⇒ **结论**：任何在 L2/L3 上跑的臂，其判据上限就是**「只披露」**——与角色③ 同姿态。**声称能在这个 n 下判出增量或非劣的方案，都是过量宣称。**

### 4.2 为什么不至于又是 H7「model ≡ base」

H7 的结局是 model 臂与 base 逐位相同。对本案，我的答案是：**默认期望确实是「又一次冗余判死」，而这正是我要先去测的东西——判死线是别人写好的，不是我加的。**

- `e2-combo-precheck.cjs:35` 写死 `RHO_KILL = 0.95`（转引 02 §C.1 给的行号与语义：「ρ̂ CI 下界 ≥0.95 ⇒ 该域组合臂判死」）。
- **盘上已有一次真实的冗余判死先例**：`L2×L3` ρ̂=**1** CI[1,1] identical=true ⇒ 判死，理由是 `l3_aci` 只调区间不调 p——「同一信号两次」（转引 02 §C.1）。
- 而 L2 的 `assigned_prob` 与基率逐行相同（我亲测 376/376）——**这本身就是「基率层复写基率」的实证**。任何只看到「题面＋基率」的源，都会落进同一个坑。

⇒ 所以第一步不是「看它多准」，而是**测它与已有五路信号的误差结构是否独立**。若 ρ̂ CI 下界 ≥0.95 ⇒ **当场判死，省下后面全部预算**；若存活 ⇒ 这个项目**第一次**在 1180 行上有了第二路信号——那才值得谈臂、谈 PREREG。**这是一个可以失败的第一步，而不是一个只会烧钱的第一步。**

### 4.3 必须点名的两条来源卫生约束（来自 13 号件）

1. **本项目与 Jev 零先验，所以历史负结果**不能**当「这类东西我们试过了」用。** 13 号件 §4.4a 全库 grep `\bjev\b` **唯一命中是本棒自己的脚本**，结论「**Jev 对本项目是一条零先验新线，因此更需要 PREREG 前置，而不是更不需要**」。我完全接受这条，并把它写进下面的最小第一步：**先冻结判死线，再看数**。
2. **「Jev」与「Jev 类」是两个词，方案里绝不能并列。** 10 号件 §3 六路交叉验证的结论是：**TypeSafe 未发布权重、无自托管、未公布参数量与架构**；榜单标题里的 `rebuild the System One **shape**` 一词才是关键——**它们复刻的是形状，不是权重**。任何「本地跑 Jev」的说法，指的必然是社区复刻。同理，11 号件 §4.6 把「真·读 logits」（SemIf/kev/nimble/decider/simple-jev）与「模型自报概率」（`LocalJev` README 原文明写 `generated/self-reported by the model rather than read directly from its logits`）分成两条**不能并列**的路线——在铁律④的语境下它们不是同一个东西。

### 6.1 术语表（概念 → 唯一标准词 ＋ 一句定义 ＋ 反例）

**纯术语，零实现细节。** 这张表的存在理由是：本轮讨论里**至少五个词正在被当成同义词用**，而它们在本项目里对应**五种完全不同的机制代价**（见 §2 表）。

| 概念 | 唯一标准词 | 一句定义 | 反例（不是它） |
|---|---|---|---|
| 让外部模型参与本项目 | **接入** | 外部模型的输出**改变了本项目任何一条既有读数或判据** | ❌ 只是把它跑一遍看数（那叫**测**） |
| 给它一个账本分类位置 | **立层** | 在账本的层枚举里新增一个取值，从而产生**分层读数** | ❌ 把它算进某个既有层（那叫**挂靠**） |

## 8. 若放行：最小第一步

**一句话**：**先做「一次冗余判死测」——把 1 个候选源的逐题 p 落成 `.scratch/jev-integration/` 下带 sha256 的 JSONL 工件，用参数化后的 `e2-combo-precheck.cjs`（`buildEngineMatrix(dbPath, extraEngines)`，默认行为逐字节不变）在现有队列上算 ρ̂／RES 两张表，对照脚本里已写死的 `RHO_KILL = 0.95` 判死；同批把「非 LLM 原生概率源是否受铁律④管」写成一张拍板单交用户。**

展开成可执行的四步（**全部零迁移、零账本写、零引擎槽位改动**）：
