## 0. 我的立场（先给结论，且给准范围）

> **【反对整合】**——反对把 Jev 类模型以「新概率源 / 新引擎臂 / 账本通路」的形态整合进本项目。

**但反对的**不是「这台机器跑不动」——恰恰相反，**这台机器跑得动**（§2.1 算术）。反对的理由是三条，按硬度排序：

1. **仪器分辨率不匹配（最硬，可复算）**：本项目自己的判据机在**可用样本量**下的 MDE 是 **0.0221**，而本项目三次实测的效应量是 **0.0014 – 0.0030**。**测量仪器的下限比它要测的东西粗 2.5–16 倍**（§4.3，我用项目自己的常数把它算出来了）。
2. **「本地 vs API」这个二分在本题上不成立**：走 Jev 托管 API 一次**全队列**通扫是 **¥0.14 – ¥3.24**（§3.2，★亲测算术）。为省这笔钱去维护一套本地推理栈，是把 ¥3 的账算成几十人时的账。**所以真问题不是「能不能本地跑」，而是「值不值得跑」。**
3. **模型的能力面撞本项目的题型**：Jev 官方自曝的失败模式里明写**「不是计算器」「不能可靠计数」「日期比较不可靠」**（□厂商宣称，10 号件取回原文）；而本项目 **9 个可出结论格里 7 个是数值/指标域**（★亲测，§4.4）。**它官方承认最弱的那一类，正是本项目题量最大的那一类。**

**我不反对的事**：任何人花 ¥0.06 做一次 30 题烟测。我反对的是把它**接进系统**。
**我的最小第一步（§7）不是「怎么接」，而是「一个 0 元 0 安装的算术，先把这件事杀掉」**——如果它杀不掉，那才算真的该做。

**我的镜头边界（不越界声明）**：本件只回答「这台机器 + Windows + 这个仓库」的落地问题。铁律④的定性、PREREG 该不该递进、账本该不该开槽位，属 03 号件与用户拍板范围，本件**只呈现工程后果，不替它们裁决**。

## 2. 问题一：本地跑，到底被什么卡住？

我把它拆成三问逐个回答：**显存？平台？维护成本？**

### 2.1 显存**不是**卡点（★亲测算术）

按 6.6 GiB 预算记账，逐个候选的权重占用（权重字节数取自 11/12/14 号件的 HTTP 实测，我未复现；GiB 折算是我本次算的）：

| 候选 | 权重实测字节（二手亲测） | GiB | + 运行时开销 ~1.3 GiB | 100% 上 GPU？ |
|---|---|---|---|---|
| 15 rlcd-modernbert-151m（`model_fp16.onnx`） | 303,785,047 | 0.28 | ≈1.6 GiB | ✅ 且**它走 CPU 也行**（编码器，KV＝0） |
| 23 Laya（`model.safetensors`） | 842,609,210 | 0.78 | ≈2.1 GiB | ✅ 余量巨大，**显存够同时驻留 3 个副本** |
| 3 PlayJev-0.8B | 2,214,590,296 | 2.06 | ≈3.4 GiB | ✅ |
| 5 NanoJev 0.6B（单个变体） | 2,385,039,280 | 2.22 | ≈3.5 GiB | ✅ |
| 12 decider-2b（bf16） | 3,763,692,048 | 3.51 | ≈4.8 GiB | ✅ **本批最大的一条也装得下** |
| 6 nimble（9B + LoRA） | 需另下 Qwen3.5-9B 基座 17.98 GiB | — | — | ❌ 显存与内存双关都过不去 |
| 7 kev-9B / 8 LocalJev(26B) / 11 openjev-sglang(B200) | — | — | — | ❌ 量级差 3–22 倍 |

**结论（★亲测算术）**：**本批所有「有真权重」的候选里，最大的一个（decider-2b 3.51 GiB）也装得进 6.6 GiB。显存不是这条路的门槛。**
这条很重要，因为它**推翻了一个常见的直觉**：人们会以为「8 GiB 笔记本 ⇒ 本地模型跑不了」，于是把「本地」当成技术问题。**它不是技术问题。**

### 2.2 平台**是半个**卡点（引用 11/12 号件，我未复现）

真正卡死的那一批，卡在**平台而不是尺寸**，而且卡的恰好是**工程上最贴的那一批**：

| 候选 | 形态（与 Jev 本体最像的一类：编码器＋选项打分头） | 卡在哪 |
|---|---|---|
| 9 Laya-MLX | MLX 原生运行时，基准环境 `M3 Max, 40 GPU cores, 128 GiB` | **Apple Silicon 专属，Windows 上不存在 MLX** |
| 13 open-jev (Dasein Labs) | `local Gemma 3 4B on Apple silicon via MLX`，自陈 `there is no container path because Linux containers cannot reach the Apple GPU` | 同上 |
| 18 Jev on a laptop | Quickstart 标题即 `Apple Silicon Mac`，`setup.sh` 装 mlx-lm | 同上 |
| 20 openjev (zhihz) | `QuickStart — Apple Silicon`、`requirements-mlx.lock.txt`、`DECISION_BACKEND=mlx` | 同上 |
| 4 Qwen-2.5-1B-RLCD | `library_name: mlx`，且**仓库内零权重**（`usedStorage: 0`） | 双重 |
| 16 LLM2Jev | README：`On Linux with a supported NVIDIA GPU, run a local model through SGLang` | Linux/Windows |
| 11 openjev-sglang | `Each container one B200 with SGLang …` | 1×B200 ≈ 180 GB HBM |

**读法（我的判断，非原文）**：**Jev 的「形状」（非自回归编码器 + 选项打分头）在开源侧的最成熟实现，几乎全部长在 Apple/MLX 上。Windows + NVIDIA 能走的只有 `torch` / `onnxruntime` 两条**。
这不是巧合：MLX 是这批复刻作者的主力工具，而 Windows 原生 vLLM **官方明确不支持**——14 号件从 `vllm/setup.py:100-107` 取到原文「vLLM only supports Linux platform (including WSL) and MacOS」，且它自己把 `VLLM_TARGET_DEVICE` 设成 `"empty"`；PyPI 侧 **297 个发布文件里 Windows wheel 数为 0**（★二手亲测，14 号件取数，我未复现）。
⇒ **Windows 上想做「Jev 形状」而非「量化 LM」的实验，可选的实现面比 Linux/Mac 窄一个数量级。**

**但这仍然不是致命项**——Windows 有 `torch`（cp313 win_amd64 轮子存在，14 号件实测 CUDA 版 2.42 GiB / CPU 版 118 MiB），只是**要装**。

### 2.3 维护成本**才是真正的卡点**（本节是我最想让人读到的一段）

我把「维护成本」拆成 5 笔可点数的账，全部有盘上证据：

**(a) 引入第二个运行时语言。** 本项目是**纯 Node 仓库**：
```
$ ls p1b/scripts/*.cjs | wc -l   →  116
$ ls p1b/scripts/*.py  | wc -l   →   1
$ head -6 p1b/scripts/README.md
> 生成时点：2026-09-20T15:47:56.668Z｜在役脚本 117 个
```
**在役 117 个脚本里，Python 占 1 个（0.85%）。** 要接任何一个本地候选，你要么装 `torch` 把 Python 面撑起来，要么直接用「已装的 CPU-only onnxruntime」——后者只覆盖第 15 条一条。

**(b) 引擎契约**逐字**写着「零网络」**，localhost 也不例外。`p1b/src/engines/l6_structural.js:6` 与 `p1b/src/engines/l2_baseline.js:10` 两处独立同文：
```
契约（纯函数：零 db / 零 LLM / 零网络）
```
⇒ **一个本地 HTTP sidecar（哪怕只绑 127.0.0.1）在字面上就不满足现役引擎契约。** 要接就得新立契约——而 03 号件 §6.6 已判这类问题为「**版本递进级设计议题**」。**这是本地路线比 API 路线更麻烦的地方，反直觉但为真**：API 调用发生在**脚本层**（`decouple9-run.cjs`、`role3-pilot.cjs` 都是这个形态，**只落工件、零账本写**），脚本层本来就有网络；而**引擎层没有**。

**有先例，且先例的边界写得很清楚**：`p1b/scripts/d2-hb.py`（PyMC 6.3.2 / Python 3.13.3，10596 B，★亲测存在）是本项目唯一活着的 Python 件。它在 2026-09-16 的 v3 研讨会上被裁定为「**降格收编**」，原文（○盘上引用，见 11-拒绝项救援-深度报告）：
> 「仅 HB/池化场景保留 PyMC」**事实上已经是现状** …… 故：**降格收编**——「PyMC=MCMC 计算库」收编为**读侧 HB 脚本**的许用工具（现状明文化），「**全量 MCMC/变分推理入管线**」**死刑维持**。

**⇒ 可直接照搬的判例**：外部 ML 栈只许活在 **scripts/ 读侧**（零账本写、零 LLM、不进 `p1b/src/engines/`）。**这条先例既给了本地路线一个合法落点，也同时把它锁死在「离线批处理」这一格**——不许做成常驻服务、不许进管线。

**(c) Windows 守护进程税，本项目刚交过一次。** 01 号件 §7.1 实测：09-21 落地的 SessionRelay 状态栈留了 **9 条** `srelay.js watch --foreground` 常驻进程，且提交正文自陈踩坑——`watch-task.cmd` **无引号**导致失败，**已加引号＋控制字符扫描**（commit `b84cf05`）。而提交里写的 pid 35824 **已经不存在了**（换代）。
**⇒ 在这台机器上「多一个常驻服务」不是零成本动作，它的故障模式（引号、控制字符、pid 换代）本项目已经真金白银付过一次。** 而本地路线**必须**有常驻服务（模型加载 3–9 s 起，不能每问一次加载一次）。

**(d) 权重落盘与磁盘。** E: 只剩 **34 GB**（★亲测 `df -h /e`），而按 11 号件的实测：NanoJev 全变体 **23.9 GB**、decider 多版本 **18.8 GB**。**任何一条都不能全量拉**，只能按需取单版本。C: 有 70 GB 且 HF 默认缓存落 C:，尚可——但这条要求「每次实验都记得只拉一个版本」，是**需要纪律去维持的运维负担**。

**(e) 上游稳定性。** 这批候选绝大多数是 **2026-09-16～09-18 建库、4–5 天龄**的仓库（11/12 号件实测 `created_at`）：其中 `jevlike` 的 `pushed_at == created_at`（建库当天推完，此后零提交）；`nimble` 与 `openjev-sglang` **连 LICENSE 都没有**（LICENSE 探针 404）。
**⇒ 把任何一个冻结到 PREREG 级的 sha 上，都建立在「4 天龄、可能没人维护、可能连许可证都没有」的地基上。** 本项目对冻结件的要求是「回链上游 sha ＋ 冲突处声明」，这对一个会消失的仓库是无法履约的。

**(f) 这三笔账加起来 = 我的结论**：本地路线的成本**不在硬件，在运维面**。它把一个「脚本层一次调用」的问题，变成「第二个运行时 + 常驻服务 + 权重版本管理 + Windows 守护进程」四件事。

## 3. 问题二：走 API 的工程形状，以及与铁律⑤的关系

### 3.1 工程形状（具体到文件与字段）

**形状**：不是服务，是**一个脚本层跑批**——完全照本项目已有的 `decouple9-run.cjs` 范式（02 号件 §C.3 实测其三条硬设计：**不写账本、只落 JSONL 工件、带调用数与费用双硬闸**）。

```
Node 进程（p1b，v24.19.0，内建 fetch，零 npm 依赖）
  │
  ├─ 读题：Node sqlite（readOnly）读 p1a.db —— 与现有脚本同法
  ├─ 组装 state：题面 + 现有 evidence 字段
  ├─ POST https://api.typesafe.ai/v1/systemone
  │     Authorization: Bearer <process.env.TYPESAFE_API_KEY>      ← key 只从进程环境取
  │     { model: "jev-1.13.0", state: <…>, questions: { q_<题号>: {type:"noul", instructions:"…"} } }
  │        ↑ 锁版本号，不用别名 jev-latest（□厂商宣称：官方建议 pin，见 10 号件 §7.1）
  ├─ ← { answers:{…}, usage:{input_tokens, output_tokens} }
  ├─ 落 p1b/sim/out/jev-shadow-<date>.jsonl（run_id 前缀命名空间）
  └─ 目标账本写 = 0；verdicts 一行不写
```

**四条接线要件**（全部照现役实现，不新造）：
1. **实验命名空间隔离**：`p1b/src/engines/l6_structural.js:29` 的 `EXPERIMENT_RUN_PREFIXES` 机制 + 该文件 `:22-27` 注释写明的理由（「任何实验批的新行都会**静默成为生产输入**」，实测 37/38 道锚题读数被改）。新源走 `run_id` 前缀登记，**零迁移**（02 号件 §C.4）。
2. **判据复用**：`require('./e2-combo-precheck.cjs')` 的 `{brier, murphyRes, bootCI}` —— 这是被 7 个脚本 require、且被 `p1b/test/role3.test.cjs:24` 测试钉死的唯一共享面。**纪律明写「禁写第二份」**（`role3-combiner.cjs:109-115`、`.scratch/p29/_append-changelog.cjs:20`）。
3. **费用硬闸**：照 `decouple9-run.cjs:55-57` 的 `MAX_CALLS=450` / `MAX_COST=¥6` / `CPC=¥0.0054 per call` 形态写死上限。
4. **端口纪律**：若坚持做本地服务，**必须避开 8787**（铁律⑨，01 号件实测 p1b 后端 Fastify 即在 8787）。14 号件已给出 8790/8791 的建议。

**不要先装 torch，先花 ¥0.06 走 API 烟测**——用 30 题、`state` 取现成 evidence 字段、`type: "noul"`、落 JSONL、**零账本写**；然后**只做一件事**：把它接到 `e2-combo-precheck.cjs::buildEngineMatrix()`（02 号件 §C.1 实测：改 `:95` require、`:139` 的 `ENGINE_KEYS`、`:147-153` 后加一行，**共约 3 行**），看两张表：
- **ρ̂ 预检**：与 L1/L6 的 ρ̂ CI 下界 ≥0.95 ⇒ 照 **L2×L3 先例判死**（省下全部后续预算）；CI 下界 <0.95 ⇒ 它才是账本上第 2 个真正独立的信号。
- **覆盖率**：它在多少题上出 `ok:true` 且 `p` 有限（照 `E2-R1-规则版` 的 `ok===true ∧ p 有限` 判据）。

**这一步通不过，就到此为止**；通得过，才谈 G0（④裁决）与 PREREG 版本递进。**顺序不能倒——③(gate) 必须先于⑥(PREREG)**。

### 我不建议的第一步（点名反对）

- ❌ **先装 `torch`（CUDA 版 2.42 GiB / 实测 4.6 min）**：在 §4.3 的问题被回答前，这是**为一个还不知能不能读的读数先付运维税**。
- ❌ **先修 WSL2 再上 vLLM**：见 §5.4，可行性未核，且**为 0.78 GiB 的模型去装一个 Linux 子系统，是把简单问题做复杂**（14 号件 §10.1 同判）。
- ❌ **先起一个常驻的本地推理服务**：撞 §2.3(b) 的引擎契约与 §2.3(c) 的 Windows 守护进程税，二者都是本项目刚付过账的坑。

## 8. 敢说不（本件三条）

1. **不该为这件事动这台机器。** 显存不是卡点（最大候选 3.51 GiB ≪ 6.6 GiB 可用，★亲测算术），平台只卡掉 Apple 专属的那一批，**而剩下的两条路（装 torch / 走 API）里，API 一次全队列只要 ¥0.14–¥3.24**（★亲测算术）。**任何以「本地省钱」为由的方案，在本题上是算错账。**
2. **这台机器不是瓶颈，这把尺子是。** 判据分辨率下限 0.0221 vs 历史效应 0.0014–0.0030（★亲测算术，且公式复现了项目自报的 n≈4704）。**在样本量解决之前，任何模型接进来都只会得到一个「未证立」——这不是模型的失败，是仪器的读数极限。**
3. **本地最匹配的那一条，自己承认零样本比猜多数类还差**（Laya: 0.362 vs majority-class 0.461，○引用其 README）。**而它的 fix 是自训，不是整合。** ⇒ 「本地跑得动」与「本地跑得出东西」是两个问题，本件回答的是后者，答案是**否**。

**最后一句给合议主编**：**本件反对的不是这个模型，是这次动作的时机。** 如果哪天 §6.1 成立（样本量上去 + 序列入库），我会是第一个说「现在可以接」的人——因为那时**这台机器仍然装得下它**。
