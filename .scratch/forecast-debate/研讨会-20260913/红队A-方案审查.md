## §1 R4 五判据逐条审（g2-report.cjs 实现对照）

判定基准：判据文本（design §4.2:143-157）vs 实现（`p1b/scripts/g2-report.cjs` 261 行工作区版）vs 库内实测（1923 行，g2_regime='R4' 全库）。

### ① 合格题累计 ≥60 —— **可以刷分，且半数池的 cutoff 腿已经恒真**

**A1｜【高】backfill 题的「cutoff 合规」检查在结构上恒真，529/1046（50.6%）池成员零区分度。**
- 实测（node:sqlite 只读）：
  `SELECT COUNT(*) FROM predictions p WHERE p.matures_at IS NOT NULL AND (...resolve.date...) IS NOT NULL AND p.matures_at = (...resolve.date...)` → **1046**；`<>` → **0**。即全库 `matures_at` 与 `evidence.resolve.date` 逐行完全相等——`matures_at` 的唯一来源是那次一次性回填（照抄 resolve.date）。
- 实现：g2-report.cjs:88-92，backfill 分支 `cutoff = matures_at − 1 天`，然后 :92 `cutoff < rd`（rd=resolve.date）。代入 `matures_at ≡ rd`：判式退化为 `rd − 1天 < rd`，**恒真**。细则 B（design:172）声称照 §4.1 修订 R3 原文「backfill 题 cutoff 必须=事件前一天」，实现用的是「**到期日**前一天」——两个概念在月窗/多日事件上不等价，且实现无从校验事件窗口起点（库里只有 resolve.date）。
- 后果：① 的「cutoff 合规」对 backfill 半壁池＝「有 matures_at」的同义词。回填批（wide 280/b4 217/backfill 152/b3 52）的入库即合格，无任何时间纪律筛查。g2-report-r4.out:6-8 实录：①=1046（backfill 529），排除桶里没有一条 backfill 因 cutoff 被拒。
- 复测：把任一 backfill 行的 matures_at 改成 rd+10 天再跑报告仍 PASS（思想实验勿执行；等价复现=上式 `<>` 计数 0）。

**A2｜【高】门行域不完整且无告警：新行默认 `g2_regime=NULL`，对门完全不可见。**
- 证据：`p1b/src/db/predictionsStore.js:60-61`（DDL `'  g2_regime TEXT,'` 无 DEFAULT）、`:81-82`（additive 迁移同）、`:184`（`INSERT INTO predictions (game_id, day, source_type, statement, assigned_prob, evidence_json, layer, secondary_layer, engine, baseline_brier, public_exposure, checklist_hash, gate)`——**不含 g2_regime/matures_at**）；g2-report.cjs:42 `REGIME = "p.g2_regime = 'R4'"`。
- 后果（双向）：正向——下一批语料（源扩量棒还在持续落库）默认 NULL，**静默掉出门域**，须再手工回填一次；R2 硬伤2 明确建议「matures_at 写端落题时算好并校验非空」，**实现只做了列迁移＋一次性回填，写端计算与校验两样都没做**。反向——不想被审的行可以用 NULL 溜出门域，报告毫无感知（没有任何「门域外行数」告警；今天恰好 regime_rows=1923=total 掩盖了这个洞）。
- 复现：`node -e` 打开内存库调 `insertPrediction`（不经迁移脚本）→ 新行 `g2_regime IS NULL`；或对生产库跑 `SELECT COUNT(*) FROM predictions WHERE g2_regime IS NULL`（现值 0，纯靠当日人工回填）。

**A3｜【中】① 的定义-实现漂移：声称的三条合取只实现了一条半。**

### ② 抽检合格率 ≥70% —— **抽样范围问题已被细则 D-2 修掉，但独立性问题是结构性的**

**A4｜【高】机器段的「契约表」＝被审数据的观测键交集——判据随写端输出自动放宽。**
- 证据：`.scratch/d2/make-audit.cjs:57`（自注「逐 kind required keys（全 R4 行观测键交集）」）＋ :68-77（reqTable 由**全部 R4 行**的 resolve 对象键求交集生成）＋ :88-89（`missing = req.filter(...)`；`contract_ok = missing.length===0`）＋ :103（`pass = resolve_present && kind_ok && cmp && slug_unique && contract_ok`）。
- 三个推论，全部可从代码直读：
  1. 写端**系统性漏写的字段自动变成非必需**（该 kind 全体都没写 → 交集里没有 → 永不 missing）；
  2. `registered_kind` 标志**不参与 pass 判定**（:103 无此项）——未注册 kind 拿到自己那行的观测键交集照样 contract_ok；

**A5｜【中】② 的独立性结构：机器段（脚本）＋语义段（同一组织的棒）＋人类校准（队长，非端用户）＋端用户 0 题。**

**A6｜【中】报告展示的候选池不是被审样本，且抽样键可预测。**

### ④ 外生难度 b(1−b)≥0.21 —— **解析而非重算的疑虑成立，且阈值数学本身有错**

**A11｜【高】「b(1−b)≥0.21 等价基率 0.35–0.65」是数学错误，实测 220/808（27.2%）的最难档落在声称区间之外。**
- 数学：x(1−x)=0.21 ⇔ x²−x+0.21=0 ⇔ x=(1±0.4)/2 → **b∈[0.30,0.70]**。[0.35,0.65] 是 b(1−b)≥0.2275 的区间，比判据窄。
- 实测（复算 ① 池逐行 parseBaseRate 后统计）：hardest=808，其中 b∈[0.30,0.35)∪(0.65,0.70]=**220 条**，b∈[0.35,0.65]=588 条。
- 影响：design:150 与 D2 §4.1 表（D2:81-84）的「等价」列错误。按 design 自己声称的区间，④ 门值应为 588（仍 ≥20，**门判定不翻转**——但文档口径与实现差 27%，且所有引用「等价 0.35–0.65」的下游表述失真）。D2 §4.1 表两列互斥：b=0.33 → b(1−b)=0.2211 → 按左列（b(1−b)≥0.21）是最难档、按右列（0.20–0.35）是中档——D2 回测报表落地时按哪列分档未定。
- 复现：`python -c "print(0.33*0.67)"` → 0.2211 ≥ 0.21；SQL/JS 复算 hardest 分带统计（本报告 §0 手段①）。

**A12｜【中】「外生」目前＝「写端算的基率可信」，无一重算；解析器脆弱但有一层意外健壮性。**
- 实测：池内可解析 b 共 933 条、**模式 100% 是 pct_share**（g2-report-r4.out:18 与本棒独立复算一致），即全部来自写端 baseRateNote 里的「占 X%」字样（g2-report.cjs:46-55 三段正则，fallback 兜底抓注记里**第一个**百分号）。design:150 禁的是 assigned_prob/判词输出/人工填值——baseRateNote 不在禁列，但它同样是**被门审查的同一批写端脚本**生成的数值，无任何独立重算或抽查（② 机器段只查「基率落带 0.15–0.85」，make-audit.cjs:95，查的是落带不是正确）。
- 意外健壮性（steelman，如实记录）：`corpus-sources-b4.cjs:179` 的 `function cmp0() { return true; }` 恒真桩使注记方向符号全批 '>='（措辞 bug，p19 锚 16:2x 已列为待修）——但 b(1−b) 对 b→1−b **对称**，方向写反不影响最难档归类，0.15–0.85 落带也对称。所以桩的现有伤害限于可读性；真正的敞口是**写端基率算错/灌值无抽查**（重算 20 条最难题的基率即可封，见 §6）。
- 覆盖缺口记账漂移：报告与复算一致=池内 113 条无可解析基率（933/1046）；p19 锚 16:0x/16:2x 两次写「池内 174 条」——同一天同一锚对同一指标出现两个数，至少一处失实（以实测 113 为准）。

## §3 D2 规格一致性审查（逐字核对 §2.2/§2.3/§3.1）

**A19｜【高】A1 断言与「最小可逆序=视图过渡」自相矛盾：视图过渡态下 A1 无法自然通过，而 G-D2-0 又只要求过渡态。**
- 逐字对账：
  - D2:41（A1）：「`SELECT outcome FROM predictions` → 失败（**no such column**）」；
  - D2:55（§3.1 最小可逆序）：「② 回测引擎以 **ATTACH 只读题面视图**运行 → ③ 验收=回测进程 SELECT truth_vault 必须失败 → ④ **再谈**物理分库」；
  - D2:57-58（G-D2-0）：「F4 接口第 **①②③** 步……未全部落地 → D2 不得开跑」（即 ④物理分库**不是**开跑前置）；
  - D2:36（§2.2 库层）：「题面库**无 outcome/truth_preview 列**」——这是物理分库后的终态，却被列为「缺一层即视为无隔离」的三层之一。
- 逻辑推演（两条分支都推给规格一个死角）：
  - 分支一（自然读法）：「题面视图」是挂真库上的一个**改名视图**（如 v_predictions_face）。回测进程里未限定名 `predictions` 解析到物理表（列还在）→ A1 **返回行** → 按 D2:40「任一失败＝D2 停跑」，隔离判不成立 → **G-D2-0 的 ①②③ 全落地也过不了 §2.3**。规格自缚。
  - 分支二（让 A1 过）：必须安排**影子主库**——回测连接以一个含无 outcome 的 `predictions` 视图的库为 main、真库 ATTACH 在后（SQLite 未限定名先解析 main）。规格**从未写这个 shadowing 安排**（§3.1 只说 ATTACH 只读题面视图）。且此时 A2 的通过完全取决于：真库里的 truth_vault 视图不被未限定名解析命中，或运行期 **authorizer 拒绝**（D2:37「sqlite authorizer/只读句柄兜底」）——A2 的合法失败模式含「denied」，意味着**隔离有效性压在一行 authorizer 配置上**，而 §3.3-1 要求的「A1/A2 盲跑断言」每批跑前重验恰好说明作者自己也知道这层是脆的。
- 结论：**G-D2-0（①②③ 可开跑）与 §2.3（A1 需 no-such-column）在视图过渡态下互斥**。修法二选一（见 §6）：要么把「影子题面库（视图名为 predictions 的 main 库）」写进 §3.1 并把 authorizer 断言升为硬验收；要么承认 A1 只有物理分库才自然满足、把 ④ 拉进 G-D2-0——后者与施工路径把物理分库放进路径 8 的 0.5–1 天打包（A18）互相顶牛，须一起裁决。

**A20｜【高】D2 回测题的落库位置自相矛盾，「不凑数」条款零机检。**
- D2:19（§1.2.5）：「**不写 p1a.db 生产表**（D2 只读题面视图）」vs D2:151（§8.2）：「D2 回测题为 **source='corpus'**（backfill 谱系），天然隔离」——source='corpus' 的题在现有体系里就是落 p1a.db predictions 表（1923 行实况即证据）。两处只能对一个。
